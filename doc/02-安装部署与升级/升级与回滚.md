# 升级与回滚

升级遵循“固定版本、升级前备份、健康验证、显式回滚”的原则。任何回滚都可能涉及数据库格式变化，不能只切回旧镜像而忽略数据恢复。

## 升级前检查

1. 阅读目标版本说明，确认数据库、插件、开放配置和业务服务兼容性。
2. 检查磁盘容量，保证当前数据与至少一份备份可同时存在。
3. 记录当前版本、镜像摘要和运行状态。
4. 在维护窗口停止写入任务，通知使用方可能的短时不可用。
5. 验证备份目标可写，并确认异地副本或外部数据库恢复点。

## Compose 升级


获取要升级的版本：

```bash
git fetch --depth=1 origin refs/heads/feature/1.2.3:refs/remotes/origin/feature/1.2.3

git switch --create feature/1.2.3 --track origin/feature/1.2.3
```

执行升级指令

```bash
./zenvisctl compose upgrade --version 1.2.3
```

工具会执行一致性冷备、把 `ZENVIS_VERSION` 更新为固定版本、拉取镜像、启动并等待健康。升级失败时不会自动猜测是否恢复旧数据，而会输出对应备份 ID。

验收至少覆盖登录、检索、看板、插件、推送任务、AI/MCP 和业务服务。确认稳定后再清理旧镜像和过期备份。

## Compose 回滚

```bash
./zenvisctl compose rollback \
  --backup compose-20260731-120000 \
  --confirm compose-20260731-120000
```

双重 ID 是防止误操作的显式确认。工具停止服务，将当前文件移到 `deploy/.zenvis/rollback-safety-*`，恢复备份中的数据、开放配置、应用配置、Compose 文件和 `.env`，然后重新健康检查。回滚安全目录不会自动删除。

## Kubernetes 升级

外部依赖必须先创建同一维护窗口的一致性备份，并取得可审计的引用：

```bash
./zenvisctl k8s upgrade \
  --version 1.2.3 \
  --external-ref backup://change-20260731-001 \
  --namespace zenvis-prod \
  --release zenvis \
  -f /secure/path/zenvis-production.yaml
```

工具先备份开放配置、Vectum 工作区和 Helm revision，再升级 Chart。`--external-ref` 只是记录外部备份的权威引用，不会替代数据库自身的备份。

## Kubernetes 回滚

先按照外部服务流程把数据库和中间件恢复到记录的恢复点，再执行：

```bash
./zenvisctl k8s rollback \
  --backup k8s-20260731-120000 \
  --confirm k8s-20260731-120000 \
  --namespace zenvis-prod \
  --release zenvis \
  -f /secure/path/zenvis-production.yaml
```

工具恢复 Helm revision、开放配置和 Vectum 工作区，并滚动重启应用。它不会自动恢复外部 MySQL、ClickHouse、Redis、Redis Stack 或 Kafka。

## 旧环境迁移

新版部署不再接受仓库中的通用默认凭据。迁移已有 Compose 环境时：

1. 先用旧版本工具创建完整备份并记录原密码。
2. 从 `deploy/.env.example` 创建 `deploy/.env`，把旧 MySQL、ClickHouse 和 Redis 凭据原样填入；不得为已有数据随机生成新密码。
3. 为 API、MCP、Vectum 和初始化账号补充新的强随机值；已有账号密码不会被重置。
4. 运行 `./zenvisctl compose doctor`，确认配置可解析。
5. 在维护窗口用目标固定版本启动并执行完整验收。

如果已有数据存在而 `.env` 缺失，`compose init` 会主动失败。这是保护机制；应从密钥管理、旧备份或运行环境找回真实凭据，而不是反复尝试。

旧版本曾把部分开发/部署默认凭据保存在可提交配置中。即使文件已改为环境变量，Git 历史仍可能保留旧值；完成迁移后应轮换数据库、Redis、Vectum、API、MCP 和模型服务凭据，并撤销旧令牌。
