# 运维与故障排查

## 日常检查

每天或由监控系统持续检查：

- Web、后端 readiness 和 Vectum health 接口；
- 容器/Pod 重启次数、CPU、内存、磁盘和 inode；
- MySQL、ClickHouse、Redis、MinIO、Kafka 的连接数、容量、延迟和错误率；
- 推送任务、AI 分析任务、插件和业务服务心跳；
- 备份完成状态及最近一次恢复演练时间。

## 先运行诊断

Compose：

```bash
./zenvisctl compose doctor
./zenvisctl compose status
./zenvisctl compose logs zenvis-backend
```

Kubernetes：

```bash
./zenvisctl k8s doctor --namespace zenvis --release zenvis \
  -f deploy/helm/zenvis/values-dev.yaml
./zenvisctl k8s status --namespace zenvis --release zenvis
kubectl -n zenvis get events --sort-by=.lastTimestamp
```

## 常见问题

### `deploy/.env` 不存在

新环境运行 `./zenvisctl compose init`。已有 `deploy/data/` 时工具会拒绝生成随机凭据，应从密钥管理或备份恢复旧密码，参阅[旧环境迁移](升级与回滚.md#旧环境迁移)。

### 镜像拉取失败

Compose 检查 `ARCH`、`ZENVIS_VERSION`、`VECTUM_VERSION` 和 `ZENVIS_IMAGE_REGISTRY`；Kubernetes 检查 `global.arch`、`global.version`、`vectum.image.version`、`global.imageRegistry`、`imagePullSecrets` 和 Pod events。确认对应固定标签存在且主机/集群具有仓库凭据。

### 后端未就绪

按顺序检查 MySQL、ClickHouse、Redis、Redis Stack、MinIO 与 Vectum 的网络、DNS、凭据和健康状态。重点搜索 `Access denied`、`Connection refused`、`UnknownHost`、迁移失败和开放配置解析错误。

```bash
./zenvisctl compose logs mysql-service
./zenvisctl compose logs clickhouse-service
./zenvisctl compose logs minio-service
./zenvisctl compose logs zenvis-backend
```

### MinIO 初始化失败

确认 `MINIO_ENDPOINT`、`MINIO_ROOT_USER`、`MINIO_ROOT_PASSWORD` 正确，账号具有创建和访问 Bucket 的权限；检查 `MINIO_BUCKET` 与四个业务 Bucket 名称非空，默认 Bucket 不与业务 Bucket 重复，四个业务 Bucket 之间也互不重复。后端启动时会自动创建缺失 Bucket，任一步失败都会中止启动。

```bash
./zenvisctl compose logs minio-service
# 本机已安装 mc 时，按 deploy/.env 替换凭据和实际监听地址
mc alias set zenvis http://127.0.0.1:19000 "$MINIO_ROOT_USER" "$MINIO_ROOT_PASSWORD"
mc ls zenvis
```

预期看到 `zenvis-attachments`、`zenvis-rag`、`zenvis-chat`、`zenvis-plugins` 和 `zenvis-reports`。不要通过改成公共匿名 Bucket 或复用默认 Bucket 绕过权限问题。

### 对象不存在或对象存储不可用

先确认 MinIO 健康、Bucket 存在且后端凭据可读。RAG 文件、聊天附件、插件包/升级快照和报表修订都直接使用对应业务 Bucket，不会回退本地文件或其他 Bucket。对象缺失时需重新上传、重新创建数据集、重新生成报表修订，或从对象存储备份恢复；不要删除 MySQL 记录来掩盖错误。

### 聊天附件无法预览或提示无权限

聊天附件只能由上传用户读取，服务端按 `chat/{userId}/fileId` 前缀校验归属。确认使用原用户会话、对象仍在 `zenvis-chat`，并且不是仅凭 `fileId` 越权访问。图片预览还要求实际文件头属于支持的图片格式。

### 旧插件提示重新上传

旧记录如果保存本地绝对路径，平台不会读取旧文件，会返回“插件包已迁移至对象存储，请重新上传并安装”。重新上传同一包名和版本的插件包后安装；存量插件包不做回填。

### 报表归档或导出失败

检查 `zenvis-reports` 中 `documents/{documentId}/revisions/{revision}/content.{md|html}` 是否存在，以及后端是否有读写权限。历史修订若没有迁移到新对象布局，需要重新生成；导出对象缺失时会重新生成，修订正文缺失时不会回退 MySQL 正文字段。

### 前端可开但接口失败

确认访问路径包含 `/zenvis/`，检查前端 Nginx 日志与后端健康。外层反向代理应保留 Host 和 `X-Forwarded-*` 请求头，不要把 `/zenvis` 重写到错误路径。

### Redis 认证失败

Compose 中普通 Redis 和 Redis Stack 共用 `REDIS_PASSWORD`，但监听端口分别为 `6379` 和 `16379`。修改密码前必须规划数据与所有客户端的同步切换；仅改 `.env` 可能导致旧数据实例无法启动。

### Kubernetes Pod Pending

执行 `kubectl describe pod` 和 `kubectl get pvc`，检查 StorageClass、卷绑定、节点架构、requests、污点和亲和性。Chart 默认按 `global.arch` 选择节点。

### 开放配置没有更新

`zenvisctl k8s init/install/upgrade` 会根据 Git 已跟踪的 `deploy/open_config/` 生成种子并写入校验和。确认文件已纳入 Git，ConfigMap 标签已变化，后端 Pod 已重新创建。运行时修改仍保存在 PVC，种子更新会合并覆盖同名文件，不会清空整个目录。

## 收集问题信息

提交问题前脱敏并附上：

- ZenVis 固定版本、CPU 架构和部署方式；
- `doctor`、服务状态和最近 events；
- 相关服务错误前后至少 100 行日志；
- 变更时间、复现步骤和预期结果；
- 是否可恢复、最近备份 ID，但不要附带 `.env`、Secret 或令牌。

不要通过删除数据目录、重建数据库或关闭认证来“验证”问题；先备份并在隔离环境复现。
