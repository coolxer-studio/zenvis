# 运维与故障排查

## 日常检查

每天或由监控系统持续检查：

- Web、后端 readiness 和 Vectum health 接口；
- 容器/Pod 重启次数、CPU、内存、磁盘和 inode；
- MySQL、ClickHouse、Redis、Kafka 的连接数、容量、延迟和错误率；
- 推送任务、AI 分析任务、插件和业务服务心跳；
- 备份完成状态及最近一次恢复演练时间。

## 先运行诊断

Compose：

```bash
./zenvisctl compose doctor
./zenvisctl compose status
./zenvisctl compose logs zenvis-backend
```

Kubernetes：

```bash
./zenvisctl k8s doctor --namespace zenvis --release zenvis \
  -f deploy/helm/zenvis/values-dev.yaml
./zenvisctl k8s status --namespace zenvis --release zenvis
kubectl -n zenvis get events --sort-by=.lastTimestamp
```

## 常见问题

### `deploy/.env` 不存在

新环境运行 `./zenvisctl compose init`。已有 `deploy/data/` 时工具会拒绝生成随机凭据，应从密钥管理或备份恢复旧密码，参阅[旧环境迁移](升级与回滚.md#旧环境迁移)。

### 镜像拉取失败

Compose 检查 `ARCH`、`ZENVIS_VERSION`、`VECTUM_VERSION` 和 `ZENVIS_IMAGE_REGISTRY`；Kubernetes 检查 `global.arch`、`global.version`、`vectum.image.version`、`global.imageRegistry`、`imagePullSecrets` 和 Pod events。确认对应固定标签存在且主机/集群具有仓库凭据。

### 后端未就绪

按顺序检查 MySQL、ClickHouse、Redis、Redis Stack 与 Vectum 的网络、DNS、凭据和健康状态。重点搜索 `Access denied`、`Connection refused`、`UnknownHost`、迁移失败和开放配置解析错误。

```bash
./zenvisctl compose logs mysql-service
./zenvisctl compose logs clickhouse-service
./zenvisctl compose logs zenvis-backend
```

### 前端可开但接口失败

确认访问路径包含 `/zenvis/`，检查前端 Nginx 日志与后端健康。外层反向代理应保留 Host 和 `X-Forwarded-*` 请求头，不要把 `/zenvis` 重写到错误路径。

### Redis 认证失败

Compose 中普通 Redis 和 Redis Stack 共用 `REDIS_PASSWORD`，但监听端口分别为 `6379` 和 `16379`。修改密码前必须规划数据与所有客户端的同步切换；仅改 `.env` 可能导致旧数据实例无法启动。

### Kubernetes Pod Pending

执行 `kubectl describe pod` 和 `kubectl get pvc`，检查 StorageClass、卷绑定、节点架构、requests、污点和亲和性。Chart 默认按 `global.arch` 选择节点。

### 开放配置没有更新

`zenvisctl k8s init/install/upgrade` 会根据 Git 已跟踪的 `deploy/open_config/` 生成种子并写入校验和。确认文件已纳入 Git，ConfigMap 标签已变化，后端 Pod 已重新创建。运行时修改仍保存在 PVC，种子更新会合并覆盖同名文件，不会清空整个目录。

## 收集问题信息

提交问题前脱敏并附上：

- ZenVis 固定版本、CPU 架构和部署方式；
- `doctor`、服务状态和最近 events；
- 相关服务错误前后至少 100 行日志；
- 变更时间、复现步骤和预期结果；
- 是否可恢复、最近备份 ID，但不要附带 `.env`、Secret 或令牌。

不要通过删除数据目录、重建数据库或关闭认证来“验证”问题；先备份并在隔离环境复现。
