# 插件包规范

插件包是 ZenVis 的最小可安装扩展单元。一个归档只描述一个稳定包名下的能力集合，平台通过目录名称识别并安装资源。

## 标准目录

```text
plugin-example/
├── index.json
├── README.md
├── icon.png
├── 00_doc/
├── 01_meta/
├── 02_push-task/
│   └── config.json
├── 03_api/
│   ├── plugin-example-api.jar
│   └── migrations/mysql/
├── 04_ui/
├── 05_dashboard/
│   ├── config.json
│   ├── low-code/
│   └── html-page/
├── 06_mcp/
│   └── config.json
├── 07_skill/
└── 08_menu/
    └── config.json
```

根目录必须直接包含 `index.json`，不能在归档中额外包一层目录。能力目录可以为空；提供配置时必须使用平台认识的目录和 Schema。

## 根文件

### index.json

```json
{
  "name": "示例分析插件",
  "package_name": "com.example.plugin.analytics",
  "version": "1.0.0",
  "description": "为示例数据提供接入、检索和可视化能力",
  "author": "Example Team",
  "icon": "icon.png"
}
```

| 字段 | 要求 |
| --- | --- |
| `name` | 面向用户的名称，保持简洁且可区分 |
| `package_name` | 插件唯一身份，使用稳定的 Java 包名风格；安装后不可通过升级修改 |
| `version` | 合法的 SemVer；升级版本必须严格高于当前版本 |
| `description` | 描述业务范围，不罗列实现细节 |
| `author` | 维护组织或作者 |
| `icon` | 插件内相对路径或平台支持的图片 Data URI |

插件内的 Dashboard Code、MCP Code、Skill ID、Entity、表名、Topic 和配置索引都应带有稳定的业务命名空间，不能依赖显示名称保证唯一性。

### README.md

插件 README 面向安装和运维人员，至少说明：

- 适用场景、能力范围和不支持的场景；
- 数据来源、Entity、表、Topic、页面与菜单映射；
- 环境变量、时区、编码、凭据注入和网络依赖；
- DLQ、重放、数据保留和卸载影响；
- 安装顺序、升级限制、验证结果和已知问题。

`README.md` 描述当前发布包；`00_doc/` 保存更详细的数据字典和对接资料。两处内容必须与实际配置一致。

### icon.png

图标应是发布包的一部分，路径与 `index.json.icon` 一致。不要引用开发机绝对路径或部署环境临时 URL。

## 能力目录职责

| 目录 | 内容 | 平台消费者 |
| --- | --- | --- |
| `00_doc` | 数据字典、对接协议、运维说明、可进入 RAG 的资料 | 插件管理、RAG |
| `01_meta` | Entity、Attribute、Operator 和 ClickHouse Schema | Meta、Retrieval、ClickHouse |
| `02_push-task` | 推送任务注册和 Vectum/Vector 配置 | 推送任务服务 |
| `03_api` | 最多一个动态 API 薄 JAR、MySQL 迁移 | 动态类加载器、迁移服务 |
| `04_ui` | 低代码应用和独立低代码页面 | 前端低代码容器 |
| `05_dashboard` | Dashboard 定义、低代码看板、HTML 看板 | Dashboard 服务 |
| `06_mcp` | 外部 MCP Server 连接描述 | MCP Client 注册表 |
| `07_skill` | 一个或多个运行时 Skill | Skill 注册表、DIH |
| `08_menu` | 插件菜单入口 | 菜单与角色权限 |

安装器按固定阶段处理这些目录，菜单最后导入。目录编号表达的是安装契约，不表示每个插件必须提供全部能力。

## 新建规范与历史兼容

| 场景 | 新建插件推荐 | 已有插件兼容 |
| --- | --- | --- |
| UI | `04_ui/<逻辑名>/site.json` 或 `index.json` | 直接把文件放在 `04_ui` 根目录 |
| 推送任务 | YAML、Source→Kafka 与 Kafka→ClickHouse 分阶段 | 稳定运行的 TOML 可继续维护 |
| Meta | 逻辑名与物理列尽量一致，显式描述字段语义 | 保留已有合法别名和兼容字段 |
| API | 插件内 `api-src` 构建一个薄 JAR | 独立 `extend-*` 工程仍可由构建脚本接入 |

兼容模式用于维持既有插件，不应成为新插件默认模板。迁移兼容格式前必须有明确收益，并按升级规则验证数据和配置身份。

## 标识与引用

| 标识 | 稳定性要求 | 常见引用方 |
| --- | --- | --- |
| `package_name` | 插件生命周期内不可变 | API 前缀、资源来源、Skill 安装目录 |
| Entity `name` | 发布后不可删除或重命名 | Retrieval、页面、Vector |
| Dashboard `code` | 全局唯一，升级时保持稳定 | Dashboard ID 与默认状态 |
| MCP `code` | 全局唯一，升级时保持稳定 | 用户连接参数、Skill 工具范围 |
| Menu `params`/匹配键 | 升级时保持稳定 | 菜单 ID、角色授权 |
| Push Task `name` | 插件内唯一，升级时保持稳定 | 运行状态与任务管理 |
| Skill `id` | 全局安全标识，升级时保持稳定 | 会话入口、显式选择 |

显示名称、描述和页面内容可以迭代；承担资源身份的字段不能随意修改。

## 文档与 RAG

`00_doc/` 会在 Embedding/RAG 服务可用时按插件来源加载。建议只放允许检索、可独立理解的文本资料：

- 完整数据字典与字段含义；
- 接入协议、错误码和兼容说明；
- 运维、DLQ 和重放流程；
- 面向业务的知识说明。

不要把密码、Token、客户地址、运行日志、大体积二进制附件、PCAP 或归档文件放入 `00_doc/`。Embedding/RAG 不可用时，插件安装可以带警告完成，文档应说明如何在服务恢复后重新处理。

## 路径与安全约束

- 所有插件内路径必须是相对路径，不能包含路径穿越。
- 图标、推送配置、HTML 看板和迁移文件的引用必须落在对应能力目录内。
- URL 只使用平台相对地址或受控的 `http/https` 地址。
- 配置中不写真实数据库密码、访问令牌、证书私钥或客户专用地址。
- JSON、YAML 和 SQL 文件使用 UTF-8；文件名保持跨平台可用。

## 发布包边界

发布归档应包含运行时所需内容，并排除：

- `api-src/`、`target/`、`node_modules/` 等源码和构建目录；
- `.git/`、`.DS_Store`、IDE 配置和本地缓存；
- `build.log`、运行日志、临时文件和旧归档；
- 测试数据、真实样本和未授权的厂商附件；
- 多个动态 API JAR 或 Spring Boot `BOOT-INF` 应用包。

构建与归档检查见[生命周期与发布验证](/03-插件开发与集成/生命周期与发布验证.md)。

## 建模前的契约矩阵

开发数据型插件前先建立并持续维护：

| 数据定义 | 代码 | Entity | ClickHouse 表 | Kafka Topic | UI 页面 | 是否结构化 |
| --- | --- | --- | --- | --- | --- | --- |
| 示例事件 | `example_event` | `example_event` | `msg_example_event` | `example-event` | `event-list` | 是 |

每个结构化定义映射到一个 Entity 和一张表。PCAP、压缩包等非结构化附件只有在规范明确定义结构化记录时才进入 Meta。
