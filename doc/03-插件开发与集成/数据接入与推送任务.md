# 数据接入与推送任务

`02_push-task` 描述插件的数据接入任务。平台保存任务定义，实际数据处理由 Vectum/Vector 执行。

## 目录与注册

```text
02_push-task/
├── config.json
├── source-to-kafka.yaml
└── kafka-to-clickhouse.yaml
```

`config.json` 是任务数组：

```json
[
  {
    "name": "示例数据接收服务",
    "description": "接收原始记录并写入 Kafka",
    "config": "source-to-kafka.yaml"
  },
  {
    "name": "示例数据入库服务",
    "description": "校验并转换 Kafka 记录后写入 ClickHouse",
    "config": "kafka-to-clickhouse.yaml"
  }
]
```

`name` 在插件内必须唯一，也是升级时保留运行状态的重要身份。`config` 可以引用 `02_push-task` 内的 `.yaml`、`.yml`、`.toml` 或 `.json` 文件；平台安装时读取文件内容并保存。

## 推荐链路

新建数据接入默认拆成两个服务：

```text
外部来源
  │
  ▼
Source → 原始记录 → Kafka 原始 Topic
                        │
                        ▼
                 校验与类型转换
                  ├── 合法 → ClickHouse
                  └── 异常 → 插件专属 DLQ
```

拆分的价值：

- 原始数据在 Kafka 保留，可重新处理；
- 来源接收和数据转换可以独立扩缩容；
- 格式错误不会污染正常表；
- 修改转换逻辑时不必重新连接外部来源。

稳定运行的历史 TOML 单任务可以继续维护。没有迁移、重放或可观测性收益时，不要只为格式统一而改写。

## Source → Kafka

第一阶段遵循来源协议接收数据，并把业务记录原样写入 Kafka：

- 不解析、重命名或删除业务字段；
- 不提前做类型转换或 Base64 解码；
- 使用 `raw_message` 等可以保留原始记录的编码；
- 来源鉴权、地址、路径和轮询周期使用环境变量；
- 文件来源要明确已处理文件、重复消费和历史文件年龄策略。

示意配置：

```yaml
sources:
  example_source:
    type: file
    include:
      - "${EXAMPLE_INPUT_PATH:-/data/incoming/*.log}"
    read_from: beginning

sinks:
  example_raw_kafka:
    type: kafka
    inputs:
      - example_source
    bootstrap_servers: "${KAFKA_BOOTSTRAP_SERVERS:-kafka-service:9092}"
    topic: "${EXAMPLE_RAW_TOPIC:-example-raw}"
    encoding:
      codec: raw_message
```

来源类型应按真实协议选择；不要把本地文件示例直接当作所有环境的生产方案。

## Kafka → ClickHouse

第二阶段负责：

1. 消费与数据定义对应的原始 Topic。
2. 校验字段数量、必填值、类型、枚举和编码。
3. 按数据字典转换时间、数字、布尔、数组或 JSON。
4. 输出与 Meta 业务 Attribute 完全一致的字段集合。
5. 把合法记录写入 Entity 对应的 ClickHouse 表。
6. 把确定性失败记录发送到 DLQ。

转换示意：

```yaml
sources:
  example_raw:
    type: kafka
    bootstrap_servers: "${KAFKA_BOOTSTRAP_SERVERS:-kafka-service:9092}"
    group_id: "${EXAMPLE_GROUP_ID:-example-transform}"
    topics:
      - "${EXAMPLE_RAW_TOPIC:-example-raw}"
    decoding:
      codec: bytes

transforms:
  map_example_event:
    type: remap
    inputs:
      - example_raw
    drop_on_error: true
    reroute_dropped: true
    source: |-
      raw = to_string(.message) ?? ""
      fields = split(raw, "|++|")
      assert_eq!(length(fields), 3, message: "example_event 字段数量必须为 3")
      . = {
        "event_id": fields[0],
        "event_time": parse_timestamp!(fields[1], format: "%Y-%m-%d %H:%M:%S"),
        "detail": fields[2]
      }

sinks:
  example_dead_letter:
    type: kafka
    inputs:
      - map_example_event.dropped
    bootstrap_servers: "${KAFKA_BOOTSTRAP_SERVERS:-kafka-service:9092}"
    topic: "${EXAMPLE_DLQ_TOPIC:-example-dead-letter}"
    encoding:
      codec: json
```

ClickHouse Sink 的地址、用户和密码必须从部署环境注入，并遵循当前 ZenVis 部署的凭据契约。文档和插件包中不要写入真实密码。

## 字段对齐

对每个结构化定义建立字段闭环：

| 环节 | 使用的标识 |
| --- | --- |
| 数据字典 | 来源字段及顺序 |
| Vector Transform 输出 | Meta Attribute 逻辑 `name` |
| ClickHouse Sink | Entity `table_name` |
| ClickHouse 列 | Attribute `column_name` |
| Retrieval / UI | Entity 与 Attribute 逻辑名称 |

转换输出不包含 `zenvis_id` 和 `zenvis_insert_time`，这两个字段由平台维护。

不要通过默认值掩盖错误。例如，无法解析的数字不能一律变成 `0`，无法解析的布尔不能一律变成 `false`。

## DLQ

以下情况默认进入插件专属 DLQ：

- 字段数量不符；
- 必填字段缺失；
- 时间、数字或布尔解析失败；
- 枚举值超出规范；
- 规范要求的解码或 JSON 解析失败；
- 目标定义无法确定。

Fallible Transform 使用：

```yaml
drop_on_error: true
reroute_dropped: true
```

并把 `<transform>.dropped` 连接到 DLQ Sink。DLQ 事件应保留：

- 未修改的原始 `message`；
- `metadata.dropped.component_id`；
- 可操作的 `metadata.dropped.message`；
- `metadata.dropped.reason`。

DLQ Topic 必须与所有正常来源 Topic 分离，避免异常记录重新进入正常链路。Topic 名称、保留期、消费责任、告警和重放流程都应写入插件 README 或 `00_doc/`。

## 编码和 Base64

- 只有数据规范明确声明重复值时才解析数组。
- 只有明确声明 JSON 时才解析为 JSON。
- 只有明确说明 Base64 解码后的内容时才解码。
- Opaque Base64、报文、规则片段和二进制载荷保持原编码。
- 可读字符串解码失败时，按数据契约保留原值或进入 DLQ，不能静默丢弃。
- 时间转换必须明确输入格式、时区和输出精度。

## 环境变量

常见变量包括：

| 类型 | 示例 |
| --- | --- |
| Kafka | Broker、Topic、Group ID、认证、批次与重试 |
| ClickHouse | Endpoint、Database、User、Password |
| 来源 | API 地址、SFTP 路径、账号、轮询周期 |
| 可靠性 | Buffer、Acknowledgement、Retry、Timeout |
| DLQ | Topic、重试、Buffer、保留和告警 |

给非敏感配置提供合理默认值；密码、Token 和客户地址不提供仓库默认值。

## 重放

重放前确认：

1. 原始记录仍然可用。
2. 新转换与目标 Meta 版本匹配。
3. 重放 Topic 不会与实时消费形成循环。
4. 业务唯一键或去重策略能接受再次写入。
5. DLQ 失败原因已修复，而不是被关闭。

重放应使用独立消费者组，并记录时间范围、来源 Topic、目标版本和结果。

## 验证

- `config.json` 可解析，任务名称无重复，引用文件存在。
- YAML/TOML 能被目标 Vectum/Vector 版本校验。
- 每个结构化定义都有明确的 Topic、Transform、Sink 和 Entity。
- Transform 输出字段与 Meta 业务 Attribute 无缺失、无多余。
- 合法样例进入正常输出；字段数、时间和类型错误进入 `.dropped`。
- 每个 `.dropped` 输出都连接到 DLQ。
- DLQ 记录保留原始消息和明确原因，不进入 ClickHouse。
- 配置中不存在真实密码、Token 和客户地址。
