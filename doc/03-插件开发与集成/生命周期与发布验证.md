# 生命周期与发布验证

插件交付不仅是生成归档，还要保证安装、升级、恢复和卸载都符合资源归属与数据安全边界。

## 状态

平台记录以下状态：

| 状态 | 含义 |
| --- | --- |
| `UN_INSTALL` | 已创建或上传，尚未安装 |
| `INSTALLING` | 正在安装 |
| `INSTALLED` | 已安装并可运行 |
| `INSTALL_FAILED` | 安装失败，可检查日志后重试或卸载 |
| `UNINSTALLING` | 正在卸载 |
| `UNINSTALL_FAILED` | 卸载失败，需要修复后重试 |
| `UPGRADING` | 正在升级 |
| `UPGRADE_FAILED` | 升级失败且自动恢复未完成，可执行恢复 |

安装、升级和卸载是后台任务。提交成功不等于操作完成，应检查最终状态、操作日志和错误信息。

## 上传

当前上传要求：

- 文件格式为 `.tar.gz`；
- 文件不为空且不超过 300 MB；
- 归档根目录包含 `index.json`；
- `index.json` 至少包含名称和合法包名；
- 图标引用的文件必须存在；
- 归档路径不能越出插件根目录。

上传只解析基础描述，不代表所有 Meta、迁移、UI、Dashboard、MCP 和 Menu 已通过安装或升级校验。

## 首次安装顺序

当前安装器按以下顺序执行：

```text
1  解压插件包
2  拷贝并加载 Meta，创建 ClickHouse Schema
3  存储 Push Task
4  执行 MySQL 迁移
5  加载动态 API JAR
6  拷贝 UI 配置
7  存储 Dashboard
8  存储外部 MCP 配置
9  加载 00_doc 到 RAG
10 安装运行时 Skill
11 创建菜单
```

安装阶段失败时，平台会尽力按补偿栈清理已经创建的运行资源。以下情况需要特别注意：

- 已执行的 MySQL DDL 不会自动回滚；
- RAG/Embedding 不可用时，安装可以带警告完成；
- Skill 加载失败时，安装可以带警告完成；
- 菜单创建在最后，不会自动给角色授权。

## 升级预检

升级前平台会：

- 解压候选包到隔离目录；
- 校验 `index.json`、图标和所有 JSON；
- 要求包名与当前插件完全一致；
- 按 SemVer 比较，候选版本必须严格更高；
- 限制 `03_api` 最多一个有效 JAR；
- 校验 UI 目录、Push Task、Dashboard、MCP 和 Menu；
- 合并候选 Meta 与全局 Meta，检查冲突和 SQL 安全；
- 检查 Meta 仅包含允许的新增式变化；
- 校验 MySQL 迁移历史、描述和 SHA-256。

预检失败不会切换当前安装目录。

## 升级执行

预检通过后，平台创建持久化快照，保存旧插件目录、Meta、UI、Dashboard、MCP、Menu、角色授权、Push Task 和 Skill 等恢复信息。

执行顺序：

```text
暂停正在运行的 Push Task，卸载旧 API
  → 执行新增 MySQL 迁移
  → 应用 ClickHouse 新增表和字段
  → 原子切换目录并替换 Meta
  → 加载新 API 和 UI
  → 更新 Dashboard 与 MCP
  → 更新 Skill 与 RAG
  → 原位更新 Menu 并保留角色授权
  → 更新 Push Task 并恢复启停状态
```

稳定标识用于保留运行状态：

| 资源 | 匹配身份 | 保留内容 |
| --- | --- | --- |
| Push Task | `name` | 原启停状态 |
| Dashboard | `code` | 数据库 ID、默认状态 |
| MCP Server | `code` | 管理员修改过的连接参数和启用状态 |
| Menu | `type + params`，或 `type + route + name` | 菜单 ID、角色授权 |
| UI | 配置索引 | 资源路径和引用关系 |

## 升级限制

- 包名不可修改，版本必须递增。
- 已有 Entity 和 Attribute 不能删除或重命名。
- 已有表、列、类型、引擎、排序键和分区键不能修改。
- 已执行 MySQL 迁移必须保留原内容。
- 当前默认 Dashboard 不能被候选包删除。
- Dashboard Code、MCP Code、Menu 匹配键和 Push Task 名称应保持稳定。
- 升级会短暂停止插件 API 和运行中的 Push Task。

MySQL 迁移和 ClickHouse 新增结构是向前变更。即使后续自动恢复旧插件，它们也不会被删除，因此迁移必须允许旧版本继续运行。

## 自动恢复和人工恢复

升级失败时，平台会尝试从快照恢复旧目录和资源，并把插件返回 `INSTALLED`，同时保留失败原因。

以下情况会进入 `UPGRADE_FAILED`：

- 自动恢复未完成；
- 快照缺失或损坏；
- 恢复旧 Meta、UI、API 或数据库资源失败。

后端启动时会检测中断在 `UPGRADING` 的记录并尝试恢复。人工执行恢复前应保留操作日志和快照，不要直接删除升级工作目录。

恢复能够还原旧运行资源，但不能撤销已经执行的 MySQL 迁移和已经创建的 ClickHouse 新表、新字段。

## 卸载影响

卸载按资源归属清理：

- 菜单和相关角色权限；
- Dashboard 与插件 HTML 文件；
- 外部 MCP 配置；
- 低代码 UI 配置；
- 动态 API 路由、Bean 和 ClassLoader；
- Push Task；
- 插件 Meta；
- Meta 声明的 ClickHouse 表及数据；
- 已安装目录；
- RAG 文档来源和运行时 Skill。

卸载不会回滚插件 MySQL 迁移，也不会删除 `t_sys_plugin_migration` 历史。插件自己的 MySQL 业务表需要单独、显式的数据治理流程。

卸载是高风险数据操作。停用、停止 Push Task 或下线菜单可以满足需求时，不应使用卸载代替。

## 导出

未安装且仍保留原始上传包时，平台可以直接导出原归档。已安装插件导出时，平台从当前运行状态重新生成：

- `index.json`、图标和文档；
- 当前 Meta；
- 当前 Push Task 配置；
- API JAR 和 MySQL 迁移；
- 当前 UI、Dashboard、MCP、Skill 和 Menu。

因此导出包可能包含平台运行期间调整过的配置，不一定与最初上传归档逐字相同。导出后仍需重新执行归档检查。

## 构建

父仓库直接维护的插件：

```bash
cd zenvis-plugin
bash build.sh plugin-example
```

Windows：

```powershell
cd zenvis-plugin
.\build.ps1 plugin-example
```

构建脚本会：

1. 查找插件内 `api-src` 或对应的独立 `extend-*` 工程。
2. 执行 Maven `clean package`。
3. 删除 `03_api` 根目录旧 JAR。
4. 复制新的薄 JAR。
5. 从插件根内容生成 `<package-name>.tar.gz`。
6. 排除 `api-src`、`.DS_Store`、旧归档和构建日志。

嵌套场景或产品插件进入 `zenvis-plugin/zenvis-plugin-*` 对应工作树，使用该子仓库声明的构建脚本。企业插件还必须按兼容矩阵完成安全、运维、升级回滚和生产验收门禁；父仓库不会替代子仓库生成归档。

macOS 构建脚本使用 GNU Tar `gtar`；运行前确保已安装。

## 归档检查

检查归档本身，不只检查源码目录：

```bash
tar -tzf com-example-plugin-analytics.tar.gz
```

必须确认：

1. `index.json` 位于归档根目录，没有多余顶层目录。
2. 包名、版本、README 和图标正确。
3. `01_meta`、`02_push-task`、`04_ui`、`05_dashboard`、`06_mcp`、`07_skill`、`08_menu` 是本次版本。
4. `03_api` 根目录最多一个薄 JAR，迁移完整。
5. 不包含 `api-src`、`target`、`.git`、日志、旧归档和真实样本。
6. JSON/YAML/TOML 可解析。
7. 不包含密码、Token、私钥和客户专用地址。

## 分层验证

### 静态契约

- 所有 JSON 可解析。
- YAML/TOML 由目标 Vectum/Vector 版本校验。
- Entity、表、Topic、Transform、Sink、UI 和 Dashboard 对齐。
- Transform 输出字段与 Meta 业务 Attribute 完全一致。
- 配置索引、Dashboard Code、MCP Code、Menu Params 和 Skill ID 无冲突。

### API 与迁移

- 运行插件 API Maven 测试。
- JAR 包含 class 且没有 `BOOT-INF`。
- Controller 路径加载后带正确插件前缀。
- MySQL 迁移可从空库执行，已执行版本不会重复执行。

### 接入链路

- 为每个数据定义准备至少一条合法样例。
- 合法记录到达目标 ClickHouse 表。
- 字段数、时间、数字和枚举错误到达 DLQ。
- 异常记录不进入正常表，DLQ 保留原始消息和可操作原因。

### 页面与 Agent

- 低代码应用、列表、详情和统计页能打开。
- HTML 看板覆盖加载、空数据、失败和刷新状态。
- Menu 指向正确配置且角色已授权。
- MCP 能连接并发现预期工具。
- Skill 只获得 Allowlist 与审批策略允许的工具。

## 常见排障

### 安装后 Entity 或页面缺失

从操作日志找到最先失败的阶段，检查归档是否含对应目录、Meta 是否可加载、配置索引是否冲突，以及菜单是否已授权。

### Kafka 有数据但 ClickHouse 无记录

检查消费者组、Transform、目标表、字段对齐和 DLQ。不要关闭校验来隐藏异常。

### 动态 API 未注册

检查 JAR 数量、包结构、扫描包、平台依赖和 Bean/路由冲突。

### 升级提示迁移校验和变化

恢复原迁移文件，用更高版本表达后续变化。

### 升级失败但插件仍可使用

这是自动恢复成功的预期状态。读取升级错误并修复候选包，不要忽略已执行的向前数据库变更。

### 卸载后数据消失

卸载会删除 Meta 关联的 ClickHouse 表和数据。恢复依赖卸载前的备份；MySQL 表不会由卸载流程自动清理。

## 交付清单

- 插件 README、`00_doc` 和所有配置描述同一版本。
- 包名、版本和所有稳定标识正确。
- 数据字典、Meta、Vector、UI 和看板一致。
- API 测试、配置解析和目标环境校验通过。
- 归档内容已检查，无源码、构建噪声和敏感信息。
- 已记录安装、升级、卸载、DLQ、重放和回滚边界。
- 只在目标插件工作树修改和构建，没有覆盖其他未提交内容。
