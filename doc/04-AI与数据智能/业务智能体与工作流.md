# 业务智能体与工作流

本文说明 ZenVis 当前六个内置业务智能体的使用方式、确定性工作流、确认与审批边界、产物生命周期和排障方法。

## 当前内置智能体

| 页面名称 | 会话类型 | 主要能力 |
| --- | --- | --- |
| 元数据配置 | `agent_metadata_config` | 生成或更新 Meta，写入并读回校验 |
| 数据推送服务 | `agent_data_push_service` | 只读校验已发布 Meta，创建、检查或修复 PushTask |
| 临时图表 | `agent_visualization_chart` | 查询真实实体数据，生成 ECharts 快照并按需加入图表库 |
| 可视化应用 | `agent_visualization_app` | 生成低代码单页、侧边栏应用或静态 HTML 页面，并按需发布菜单 |
| 数据大屏 | `agent_visualization_dashboard` | 生成低代码或 HTML 看板，完成 Dashboard 与菜单读回 |
| 报表制作 | `agent_report` | 汇总会话内容与图表库快照，生成、编辑、修订、归档和导出报表 |

运行时入口来自 `skill_config` 中已启用的 Skill 配置。管理员禁用对应 Skill 后，入口和实际执行能力会相应变化。

插件制作不是当前内置业务智能体。插件或客户专项能力应通过已启用的 `skill:<skillId>` 聊天入口提供，仍受 Skill 工具白名单、MCP 策略和资源预算约束。

旧 `agent_data_visualization` 会话类型、`data_visualization.*` 动作和 `dataVisualization` 结果分区不再被新入口接受。历史会话、旧卡片和旧协议不做迁移或别名兼容；旧 `dataVisualization.chartLibrary` 仅作为惰性历史数据保留，不展示、不进入报表图表库。

## 共同运行边界

- 业务智能体只在所选 Skill 绑定知识库的并集内自动检索 RAG；未绑定知识库时不检索，也不回退全库。
- `deep_think=true` 不改变业务智能体的 Workflow、Skill 或工具权限。
- Agent 不能用自然语言声明代替真实工具结果。
- 业务确认、MCP 审批、工具执行和读回验证是独立阶段。
- 服务端保存工作流状态、候选快照、证据和修订号，前端不能通过修改卡片跳步。
- 达到工具预算、重复失败上限或上下文上限后，应基于已有证据停止或给出阻塞原因。
- 启用持久化运行的 Agent 由 Agent Run 保存计划、检查点和事件；关闭页面后仍可继续，运行中消息作为 steer 在当前步骤结束后应用。
- 每个业务轮次的回复都保留独立运行卡，执行过程默认折叠展示该轮的 RAG 检索、工具调用和上下文压缩。多轮会话刷新后仍按消息 `runId` 恢复历史卡片。
- Run 进入 `WAITING_USER` 时自动展示完整补充问题；提交后通过 steer 继续原计划，关闭弹窗只会暂缓处理，不会结束任务。
- 未启用持久化运行的 Agent 继续使用同步单轮执行，两者共享 Skill、工具策略和审批审计边界。

## 工作流与证据

业务智能体共享工作流基础设施，但每个定义只生成和接受本领域步骤。卡片通常包含：

- `workflowId`、`workflowVersion`、`stateRevision`；
- 当前 `step`、对象类型和允许动作；
- `evidenceRefs` 和校验状态；
- 服务端锁定的候选、查询或配置摘要。

用户提交动作时，服务端精确校验会话、消息、part、工作流、状态修订号和允许动作。旧卡片、过期修订、被篡改候选或不允许的跳步操作会被拒绝。

### 业务确认与 MCP 审批

| 机制 | 决定什么 | 不能替代什么 |
| --- | --- | --- |
| 业务确认卡 | 是否采用实体、字段、查询方案或候选配置 | 不能批准高风险工具 |
| MCP 审批卡 | 某一次 `ASK` 工具是否执行 | 不能替代业务方案确认 |
| 读回验证 | 写入结果是否与已确认内容一致 | 不能由模型文字声明代替 |

业务卡通常调用 `/api/v1/dih/chat/workflow/action`，工具审批调用 `/api/v1/dih/mcp/approvals/{requestId}/decision`。完整字段见[DIH 与 AI API](/08-API参考/RestfulAPI/DIH与AI.md)和[MCP 服务管理 API](/08-API参考/RestfulAPI/MCP服务管理.md)。

## 元数据配置

元数据配置只推进 Meta 全流程，不生成推送任务，也不串联其他智能体。

### Meta 流程

```text
信息收集
  → config_tree
  → config_schema
  → config_validate（最多 3 轮）
  → 候选配置确认
  → 写前重查
  → 可选覆盖确认
  → config_add / config_apply
  → config_read
  → 完成或阻塞
```

目录或文件操作使用独立分支：

```text
META_OPERATION_DISCOVERY
  → config_tree（必要时 config_read）
  → 锁定 sourcePath / targetPath / operationDigest
  → META_OPERATION_CONFIRMATION
  → config_rename / config_delete
  → META_OPERATION_APPLY
  → 严格重载 Meta、刷新 Schema、核验路径与内容
  → 完成或阻塞
```

运维规则：

- 候选配置的完整内容、摘要、目标目录和文件名在确认后锁定。
- 新文件按创建、应用、读回的顺序执行；`config_add` 只创建空文件并立即写入 `created` 记录，正文只在 `config_apply` 阶段写入。已有文件内容不同时必须单独确认覆盖。
- 同名同内容可以按幂等成功处理。
- `config_read` 与候选 JSON 语义一致前，不得标记为应用成功；但文件已真实写入时仍要保留 `written` 记录，并单独标记应用失败。
- “添加配置到系统”只表示进入写入阶段，高风险工具仍逐次应用 MCP 策略。
- 重命名只允许同一父目录内修改单个名称，禁止跨目录移动和目标覆盖；删除非空目录必须显式递归确认。
- 改名/删除不经过 `config_add/config_apply`，不重写正文；批准后服务端只使用卡片锁定的路径和摘要执行。
- 源文件内容、目录成员、目标占用或配置树证据变化时，确认卡失效并要求重新发现。
- Meta 操作完成后必须严格重载并刷新 Schema。文件系统已变更但重载失败时返回 `changed=true/applied=false`，保留现场并允许重试，不得声明成功。
- 右侧记录由服务端在真实执行与核验后写入：改名原位保留旧文件名并标记 `renamed`，删除保留 `deleted` 墓碑；模型输出的记录卡不能修改右侧记录。
- 元数据配置工具白名单为 `config_tree/config_schema/config_read/config_add/config_apply/config_validate/config_rename/config_delete`；其中 `config_rename/config_delete` 不授予其他智能体。

### 元数据配置排障

| 现象 | 检查 |
| --- | --- |
| Meta 没有生成 | `config_tree`、候选确认和工作流修订是否有效 |
| 写入后没有成功卡片 | MCP 审批、`config_apply` 和 `config_read` 是否全部成功 |
| 同名文件没有覆盖 | 是否展示并确认了独立覆盖卡 |
| 候选被拒绝 | 是否修改了锁定文件名、内容摘要或计划 ID |
| 改名或删除未执行 | `config_tree` 证据、目标占用、递归确认和 MCP 审批是否有效 |
| 文件已改名但应用失败 | 严格 Meta 重载或 Schema 刷新是否失败；现场应保留并要求 retry |

## 数据推送服务

数据推送服务只推进 PushTask 全流程。它唯一的业务输入依赖是已发布 Meta 的只读契约；不存在 Agent 间自动调用。

### PushTask 流程

```text
Meta 只读校验
  → 候选任务确认
  → 格式检测
  → sourceMark 冲突检查
  → 创建或复用
  → 状态读回
  → system 日志验证
  → 有证据修复
  → 完成或阻塞
```

- 多个同 `sourceMark` 任务冲突时停止，不猜测目标。
- `config_tree` 与 `config_read` 只用于校验 Meta，推送工具不包含 `config_add/config_apply`。
- Meta 变化后必须重新生成并确认推送配置，不静默沿用旧 `metaRef`。
- 缺失 Meta 时输出 `missing_meta` 卡并提供“前往元数据配置”深链，不调用写工具。
- 创建响应异常后先按 `sourceMark` 读回，避免重复创建。
- 成功记录需要唯一任务、运行状态和本轮 system 日志证据。
- 自动修复只针对日志已经证明的问题；网络、认证、权限和密钥错误直接阻塞。
- 异常数据和正常数据必须按插件任务约定进入对应输出或 DLQ。

### 数据推送服务排障

| 现象 | 检查 |
| --- | --- |
| 提示缺少已发布 Meta | 目标 Meta 是否存在，实体与字段是否满足推送配置 |
| 创建出重复任务 | `sourceMark` 是否稳定，创建异常后是否先执行读回 |
| 任务存在但无数据 | Vectum、Kafka、源地址、转换、ClickHouse 和 DLQ |
| 修复反复失败 | 查看当前轮 system 日志，不允许无证据连续改配置 |

## 临时图表

临时图表只把真实查询结果渲染为当前会话可预览的 ECharts 快照；用户确认后，由服务端把已验证快照复制到图表库。它不会创建配置、Dashboard 或菜单。

### 契约

| 项目 | 值 |
| --- | --- |
| Agent 类型 | `agent_visualization_chart` |
| Skill ID | `visualization-chart-agent` |
| Workflow | `visualization_chart` |
| 决策卡 | `zenvis:visualization-chart-decision` |
| 动作前缀 | `visualization_chart.*` |
| 成功记录 | `zenvis:visualization-chart-record` |
| 分区 | `visualizationChart.chartLibrary` |

### 流程

```text
INTENT_CONFIRMATION
  → ENTITY_META / ENTITY_SELECTION
  → ATTRIBUTE_META
  → QUERY_PLAN_CONFIRMATION
  → DATA_QUERY
  → ARTIFACT_READY
  → 可选 add_to_library
  → 真实图表库记录
```

- 实体必须来自本轮实体 Meta 工具返回，字段必须使用已选择实体的准确逻辑 `name` 再查询。
- 查询确认卡展示实体、字段角色、指标、维度、过滤、排序、目标工具和完整参数；自由输入、过期候选、物理表名、物理列名和编造字段会被拒绝。
- 批准后平台严格执行卡片中的 `query.tool/query.request`，不接受 Agent 重新生成请求或传入任意 SQL。
- 只有 `visualization_chart.add_chart_library` 可以复制已验证快照；预览、刷新和入库均复用同一安全查询。
- 工具白名单只有 retrieval 元数据与实体查询工具，不包含任何 `config_*`、`dashboard_*`、`menu_*` 或 `push_task_*`。
- Skill 预算为 16 次工具调用、32,000 累计字符和 24,000 累计 Token。

### 查询工具

| 需求 | 典型工具 |
| --- | --- |
| 指标卡 | `entity_summary` |
| 时间趋势 | `entity_trend` |
| 计数 TopN | `entity_distribution` |
| 多指标聚合、透视或热力图 | `entity_aggregate` |
| 数值分布 | `entity_histogram` |
| 相关性或气泡图 | `entity_scatter` |
| 明细 | `retrieval_search`、`entity_list` |
| 关系与时间线 | `entity_relations`、`entity_relation_timeline` |

查询失败、Meta 变化或审批拒绝后不沿用旧快照，也不生成图表库记录。刷新失败保留原入库快照；缺少安全查询参数的历史记录不能刷新。

## 可视化应用

可视化应用把真实查询结果写入低代码单页、侧边栏应用或静态 HTML 页面，并在用户单独确认后发布菜单。它不创建 Dashboard，也不写入临时图表库。

### 契约

| 项目 | 值 |
| --- | --- |
| Agent 类型 | `agent_visualization_app` |
| Skill ID | `visualization-app-agent` |
| Workflow | `visualization_app` |
| 决策卡 | `zenvis:visualization-app-decision` |
| 动作前缀 | `visualization_app.*` |
| 成功记录 | `zenvis:visualization-app-record`，以 `recordKind=config|menu` 区分 |
| 分区 | `visualizationApp.configs`、`visualizationApp.menus` |

### 流程

```text
INTENT_CONFIRMATION
  → ENTITY_META / ENTITY_SELECTION
  → ATTRIBUTE_META
  → QUERY_PLAN_CONFIRMATION
  → DATA_QUERY
  → ARTIFACT_READY
  → PERSIST_CONFIRMATION / 可选覆盖确认
  → PERSISTING
  → READ_BACK_VERIFICATION
  → 配置成功记录
  → 可选 MENU_CONFIRMATION
  → MENU_PUBLISHING
  → MENU_READ_BACK
```

- 工具白名单包含 retrieval、`config_tree/config_ensure_root/config_add/config_apply/config_read` 和 `menu_*`，不包含 `dashboard_*`、`push_task_*` 或 Meta 写工具。
- 写前计划由服务端锁定；配置内容、目标文件、`configType`、`configIndex` 或菜单参数变化后必须重新生成确认卡。
- 同名文件内容不同时必须单独确认覆盖；写入后必须由 `config_read` 读回一致。
- 菜单创建前检查类型、父级和同名入口，创建后必须由 `menu_view` 读回。菜单确认拒绝时保留已成功配置，但不生成菜单记录。
- 查询数据只用于生成配置，不进入 `visualizationChart.chartLibrary`。
- Skill 预算为 32 次工具调用、64,000 累计字符和 48,000 累计 Token。

## 数据大屏

数据大屏把真实查询结果写入低代码或静态 HTML 看板，确定性完成配置与 Dashboard 读回，再按需发布配置管理菜单。它不生成普通可视化应用配置，也不写入临时图表库。

### 契约

| 项目 | 值 |
| --- | --- |
| Agent 类型 | `agent_visualization_dashboard` |
| Skill ID | `visualization-dashboard-agent` |
| Workflow | `visualization_dashboard` |
| 决策卡 | `zenvis:visualization-dashboard-decision` |
| 动作前缀 | `visualization_dashboard.*` |
| 成功记录 | `zenvis:visualization-dashboard-record`，以 `recordKind=config|dashboard|menu` 区分 |
| 分区 | `visualizationDashboard.configs`、`visualizationDashboard.dashboards`、`visualizationDashboard.menus` |

### 流程

```text
INTENT_CONFIRMATION
  → ENTITY_META / ENTITY_SELECTION
  → ATTRIBUTE_META
  → QUERY_PLAN_CONFIRMATION
  → DATA_QUERY
  → ARTIFACT_READY
  → PERSIST_CONFIRMATION / 可选覆盖确认
  → PERSISTING
  → READ_BACK_VERIFICATION
  → config_read
  → dashboard_create
  → dashboard_view
  → 配置与看板成功记录
  → 可选 MENU_CONFIRMATION
  → MENU_PUBLISHING
  → MENU_READ_BACK
```

- 工具白名单包含 retrieval、配置工具、`dashboard_create/dashboard_list/dashboard_view` 和 `menu_*`，不包含 `push_task_*` 或 Meta 写工具。
- 配置、Dashboard 名称、code、类型、`configIndex` 和菜单参数由服务端锁定；任一参数变化后必须重新确认。
- 已存在同名或同 code 但内容不同的 Dashboard 时阻断，不覆盖、不重复创建。
- `config_read`、`dashboard_create`、`dashboard_view` 和必要的 `menu_view` 全部成功且字段一致后才生成对应成功记录。
- 菜单确认拒绝或发布失败时保留已成功的配置与看板，但不得伪造菜单记录；不新增看板专用 MenuType。
- Skill 预算为 32 次工具调用、64,000 累计字符和 48,000 累计 Token。

### 可视化边界与排障

- 三个智能体都只读依赖已发布 Meta；缺少 Meta、实体或字段时停止执行，并使用本领域决策卡返回 `missing_meta` 和前往元数据配置的预填深链。
- 深链只预填提示词，不自动发送，也不自动调用其他智能体；三个智能体之间没有自动串联或跨领域续跑。
- 只有临时图表可以产生图表库记录；应用和大屏的查询结果只用于生成配置。
- 实体或字段没有选项时检查 Meta 工具和 `evidenceRefs`；查询确认后没有产物时检查批准工具与参数是否一致。
- 图表无法渲染时检查 `echartsOption` 是否为纯 JSON，并查看 `chart_render_failed` 遥测。
- 看板或菜单未出现时检查 MCP 审批、`config_read`、`dashboard_view` 和 `menu_view` 读回。

缺失 Meta 的 handoff 使用本领域决策卡类型，结构如下：

```json
{
  "kind": "missing_meta",
  "handoff": {
    "targetAgentType": "agent_metadata_config",
    "label": "前往元数据配置",
    "prompt": "请为 <实体文件> 创建并发布 Meta：实体 <entity>，目标表 <table>，字段包括 <fields>。"
  }
}
```

前端只通过 `service-dih` 新会话深链预填该提示词，不会自动发送。旧 `dataVisualization.chartLibrary` 不迁移到 `visualizationChart.chartLibrary`；报表图表库只读取后者。

## 报表制作

报表制作由中间对话区和右侧文档工作台组成：

- 对话区负责指令、附件和 AI 生成；
- 工作台负责当前文档、人工编辑、自动保存、修订、归档、恢复和导出。

### 图表库与来源

报表工具栏的“图表库 N”不再混合展示附件、消息、分析产物和报表记录，只展示当前用户在所有临时图表会话中已执行“加入图表库”的图表：

- 服务端通过 `GET /api/v1/dih/report/chart-library` 聚合当前用户的 `visualizationChart.chartLibrary`，按图表 ID 或 `artifactId` 去重并保留最新 `addedAt`，按加入时间倒序返回。
- 返回项包含图表 ID、`artifactId`、名称、类型、描述、来源、加入/查询时间、会话记录 ID、会话标题和完整 ECharts option。损坏的会话 JSON 或空配置记录不会影响其余图表。
- 前端每次打开弹窗都重新请求接口，不依赖首次页面加载时的缓存；搜索覆盖图表名称、来源会话标题和图表类型。缺少 ECharts option 的图表仍可被检索和展示来源，但禁用预览与插入。
- 选中图表后直接在当前光标插入静态图片。前端离屏渲染为 960×540、2 倍像素白底快照，图片后追加“图表：名称”说明；无法恢复有效光标时追加到文档末尾。一次插入一张，可重复插入。
- PNG data URI 超过约 800k 字符时降级 JPEG。降级后仍超出报表 2,000,000 字符正文容量、配置缺失或渲染失败时中止插入，不修改正文。
- 插入成功后合并紧凑图表来源并触发自动保存。`source_refs` 只保存 ID、名称、类型、会话和时间等追溯字段，不重复保存完整 ECharts option。保存失败时保留本地图片并显示未保存状态。
- 插入内容是不可交互的静态快照；图表库后续刷新或删除不会改变正文。历史文档中已存在的附件、分析产物等非图表来源继续保存和展示。

服务端重新校验来源：新增图表引用只能来自当前用户的图表库，伪造或越权引用会被丢弃；历史非图表来源按原引用保留，避免旧文档来源丢失。缺失或冲突来源保留为“待确认”，Agent 不得编造证据。

对话中的图片附件仍采用分阶段处理：先提取图片证据，再把证据交给允许使用只读工具的报表阶段；不会因为本轮有图片就放开或禁用全部工具。该附件链路与“图表库”选择器相互独立。

### 完整生成与选区改写

- 持久化报表 Run 先创建草稿，再按章节调用 `report_upsert_section` 或 `report_replace_section`；每次成功写入立即保存，最后由 `report_finalize` 生成不可变修订。
- 单章节目标约 1,200 个中文字符，硬上限 2,400 字符；修改类请求只重写受影响章节。
- 旧单轮模式下的完整生成或整篇重写返回 `report-document`，更新当前文档并生成修订。
- 选区润色、缩写或扩写返回 `report-fragment`，不进入完整文档保存链路。
- 选区结果应用前再次校验文档版本、全文哈希和原片段哈希。
- 生成期间原文变化时只显示预览，不覆盖错误位置。

### 保存、修订和归档

```text
AI 完整生成或人工保存
  → 稳定 documentId
  → revision 递增
  → 用户显式归档
  → 不可变 artifact
  → 恢复后生成新的 revision
```

- 保存和完整生成携带 `base_revision`。
- 服务端使用乐观修订控制；旧版本写入返回 HTTP 409，不覆盖新内容。
- 当前正文、历史修订和不可变归档分别保存。
- 只有用户显式归档才创建 artifact；AI 生成不会自动归档。
- 重命名只修改归档名称，恢复不会倒退当前修订号。

### 导出

| 格式 | 实现 |
| --- | --- |
| Markdown | 前端下载当前规范正文 |
| HTML | 前端下载净化后的完整 HTML |
| DOCX | 服务端导出 |
| PDF | 服务端导出 |

DOCX/PDF 导出以当前 Markdown 或 HTML 为源，处理表格、链接、图片、代码块和嵌套列表。图表以 data URI 内嵌，Markdown、HTML、DOCX 和 PDF 均可显示；DOCX 按 A4 正文宽度等比缩放图片，PDF 导出前将正文转换为合法 XHTML 以兼容 data URI。报表内容或来源包含敏感数据时，下载和归档前应按业务要求脱敏。

### 报表排障

| 现象 | 检查 |
| --- | --- |
| 完整生成没有更新右侧文档 | Run 是否成功执行 `report_finalize`；旧模式是否返回有效 `report-document` |
| 报表任务停在暂停状态 | 查看 `pausedReason`、预算、`OUTPUT_TRUNCATED` 或 `UNKNOWN_TOOL_RESULT`，处理后在任务中心继续 |
| 保存提示冲突 | 重新加载最新 revision，合并后再保存 |
| 选区结果替换错位 | 文档或选区哈希已变化，应只使用预览 |
| 归档没有出现 | 是否显式执行归档；普通保存只产生 revision |
| DOCX/PDF 导出失败 | 当前文档、格式、图片资源和后端导出日志 |
| 图表库为空或缺少刚加入的图表 | 是否为当前用户、是否已执行“加入图表库”，并重新打开弹窗触发刷新 |
| 图表预览空或插入按钮禁用 | 检查 `echartsOption` 是否为非空纯 JSON；无快照记录不可插入 |
| 图表插入后保存失败 | 检查报表剩余容量、网络和后端保存日志；本地正文图片会保留，可重试保存 |
| DOCX 中图表被拉伸 | 确认导出器按图片原始宽高比和正文宽度计算尺寸，不使用固定 500×300 |

## 确定性无模型演示

开场白中的精确示例在模型可用性检查前路由：

- 元数据配置：用户事件完整 Meta 配置演示；
- 数据推送服务：只读校验已发布用户事件 Meta 并创建 PushTask 演示；
- 临时图表：创建临时图表并加入图表库；
- 可视化应用：单页面应用、带侧边栏应用和添加菜单；
- 数据大屏：低代码看板、HTML 看板和菜单入口；
- 报表制作：四个固定报表示例。

演示不是普通自由输入的模糊兜底。配置、任务、看板和菜单等写操作仍调用真实 MCP，并进行读回验证。

为了展示真实审批，内置演示的默认 `ASK` 写工具强制逐次审批：

- 既有 `ALLOW` 覆盖或会话授权不能跳过演示审批；
- 演示只提供“允许本次”和“拒绝执行”；
- 全局 `DENY` 始终优先。

## 失败账本与重试

工作流记录失败阶段、工具、请求摘要、真实错误、可重试性、检查点和已保留产物。

- 读操作瞬时失败可以有限重试。
- 写操作不盲目重试，依赖幂等标识和读回判断。
- 审批拒绝、配置读回不一致、任务不唯一或日志存在错误时，不生成成功记录。
- 重试必须从服务端给出的检查点继续，不能重新使用旧卡片绕过状态版本。

## 运维验收

- 六个内置入口与 Skill 启用状态一致；
- 普通问答入口没有获得业务 Agent 工具；
- 元数据候选、写入和读回链完整；
- 数据推送服务只读 Meta、任务创建、状态读回和 system 日志链完整；
- 可视化实体、字段和查询方案来自真实 Meta；
- 图表入库、预览和刷新复用同一安全查询；
- 看板、菜单和配置创建后完成读回；
- 报表保存冲突不会覆盖新正文；
- 报表 Run 分章节写入后只生成一个新修订，其他已完成章节不因当前章节失败而丢失；
- Markdown、HTML、DOCX 和 PDF 导出符合当前文档；
- 演示可在无模型环境进入，但不能绕过 MCP 审批和 `DENY`。
