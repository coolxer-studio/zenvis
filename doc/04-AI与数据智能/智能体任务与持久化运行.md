# 智能体任务与持久化运行

智能体任务（Agent Run）是 DIH 业务智能体的持久化执行模型。它把用户目标、计划、步骤状态、待审批动作、事件和产物保存到 MySQL，由后台调度器继续执行；关闭页面、刷新浏览器或服务重启不会自动丢失任务。

普通问答 `ask` 仍使用轻量单轮流式路径，不创建 Agent Run。后台 AI 分析任务是另一套调度机制，区别见[AI 分析任务与 Skill](/04-AI与数据智能/AI分析任务与Skill.md)。

## 统一执行模型

除普通问答 `ask` 外，所有 DIH 业务智能体任务都使用 Agent Run，包括数据接入、数据可视化、报表制作和 `skill:<skillId>` 专项 Skill。任务分类不再决定是否具备持久化能力，只决定使用哪套 Skill、工具白名单和产物协议。

- `app.ai.agent-run.enabled-types` 默认是 `*`，表示所有业务 Agent 类型统一启用。
- 需要灰度或应急回滚时，可显式配置类型白名单，或使用 `app.ai.agent-run.disabled-types` 临时停用单个类型。被停用类型继续走旧单轮流式路径。
- 业务工作流中的确认卡、补充信息卡和后续选择卡都由 Run 持久化。模型产生需要用户操作的卡片时，Run 进入 `WAITING_USER`，不会在后台重复执行或空转；用户完成卡片操作后，续跑请求以 steer 形式恢复同一个 Run。
- 结构化卡片和最终答复使用与普通流式路径相同的消息解析、工作流装饰和 `extraData` 合并流程，消息记录携带 `runId`，刷新会话后仍可继续操作。
- `POST /api/v1/dih/chat` 对已启用类型也兼容创建 Run，并把 Run 事件映射为原有的 `delta`、`tool_call`、`approval_required`、`done` 和 `error` 事件。
- 新的前端和需要断线恢复的客户端应直接使用 Run API，而不是依赖兼容适配器。
- 内置示例提示词属于确定性演示夹具，不是真实业务任务：它们仍优先走示例流式链路，不创建 Run。直接调用 Run API 提交示例时返回 `503`，客户端应回退到聊天示例链路。

首期不增加任意 Shell、任意代码执行或任意文件系统访问。工具仍受 Agent scope、Skill allowlist、MCP 策略和审批约束。

## 页面入口

- “智能体运行”入口位于对话头部操作区，与队列状态、分析任务并列；左侧会话栏只保留新建会话和会话列表。
- 运行中的业务任务在聊天区显示一张运行卡，包含任务状态、计划步骤、预算和暂停原因；内部步骤不逐条刷成普通聊天消息。
- 运行卡固定提供默认收起的“执行过程”，收起时只展示知识库检索、工具调用和上下文压缩的计数；展开后显示命中数、失败数、耗时、节省 Token 摘要和活动时间线。RAG 命中片段、工具参数与结果、压缩摘要仍需再展开单条记录，不在首屏出现。
- 多轮会话按消息上的 `runId` 为每一轮恢复各自的任务卡；刷新、完成事件触发重新加载或断线重连后，历史轮次的任务卡不会因当前 Run 刷新而被移除。
- 任务进入 `WAITING_USER` 时自动弹出补充信息输入框，问题优先读取 `pendingAction.question` 的完整内容。关闭弹窗只表示稍后处理，同一问题不会反复弹出；运行卡中的“补充信息”按钮可以重新打开。
- `ask` 等非 Run 链路继续使用原有独立 RAG/工具活动卡；Run 链路以 Run 事件表为唯一事实来源，不把活动明细重复写入最终消息。
- 已完成或刷新后的任务首次展开“执行过程”时，按 Run ID 和活动事件类型分页读取历史；运行中的任务同时接收实时事件并按稳定 ID 合并。
- 任务完成后显示最终答复。报表任务还会通过 `artifact.updated` 和 `run.succeeded` 刷新右侧文档。
- 任务中心复用同一执行过程视图，支持按状态筛选、打开原会话、查看计划与活动、审批、暂停、继续和取消；原始事件列表保留但默认折叠，供排查使用。
- 组件卸载或关闭页面只断开事件连接，不取消 Run。只有用户点击“停止”才调用取消接口。
- 运行期间输入框保持可用。针对同一会话的新消息会进入当前 Run 的 steer 队列，并提示“已排队，将在当前步骤结束后应用”。

## 状态机

| 状态 | 含义 | 是否终态 |
| --- | --- | --- |
| `QUEUED` | 已创建或重新入队，等待 worker | 否 |
| `RUNNING` | 已由某个实例认领并执行 | 否 |
| `WAITING_APPROVAL` | 等待 MCP 工具审批 | 否 |
| `WAITING_USER` | 缺少必须由用户提供的信息 | 否 |
| `PAUSED` | 达到预算、连续失败、输出截断或用户暂停 | 否 |
| `SUCCEEDED` | 计划完成、产物校验通过并写入最终答复 | 是 |
| `FAILED` | 不可恢复错误或租约连续过期 | 是 |
| `CANCELING` | 已请求取消，等待执行线程退出 | 否 |
| `CANCELLED` | 已取消 | 是 |

等待审批、等待用户和暂停状态不持有 worker 租约，也不占用并发执行槽。终态任务不会阻止同一会话创建下一个 Run。

## 补充信息交互

模型只有在缺少用户才能提供的信息时才调用 `run_request_user`。Run 随后进入 `WAITING_USER`，并把问题写入 `pendingAction.question`；会话消息中保留对应的业务卡片，用户无需重新创建任务。

- 运行卡和任务中心详情都会展示完整问题。`pausedReason` 只用于兼容旧任务或展示短原因，不能被当作完整问题来源。
- 不提供独立的补充信息弹窗。聊天页统一使用底部主输入框回答等待中的任务，避免与业务确认卡形成重复入口。
- 任务中心只展示问题和“去会话处理”按钮；用户跳转会话后在主输入框继续。
- 提交内容调用 `POST /runs/{runId}/steer`。后端清空过期的 `pendingAction`，将 Run 置为 `QUEUED` 并释放等待状态；后续模型步骤读取该 steer 后继续原计划。
- 状态轮询、事件重放和切换会话不得额外弹出补充信息输入框。

## 会话恢复与多轮任务卡

同一个会话可以顺序创建多个 Run，每条用户消息和对应的 AI 消息都会保存 `runId`。前端不能只根据“当前活动 Run”渲染任务卡，否则任务完成后刷新会话会只剩最后一张卡。

- 首屏加载会话后，分页读取该会话的全部 Run 快照，并只把消息中实际引用的 Run 恢复到对应轮次。
- 任务卡优先挂到同一 `runId` 的 AI 消息；不能挂到用户气泡，也不能用当前 Run 覆盖其他历史轮次。
- 收到 `run.waiting_user` 或 `run.succeeded` 后，先重新加载会话消息，再恢复该会话全部已引用 Run，最后同步当前 Run 的实时事件。
- 只对 `QUEUED`、`RUNNING`、`WAITING_APPROVAL`、`WAITING_USER`、`PAUSED` 和 `CANCELING` 中的活动 Run 建立事件订阅；已完成的历史 Run 只读取快照和按需加载活动事件。
- 渲染卡片的临时状态不能作为事实来源。刷新、切换会话和断线重连都必须能从消息 `runId`、Run 快照和事件表恢复。

## 执行过程

任务卡首屏只显示状态、计划、步骤和“检索 / 工具 / 压缩”摘要，详细活动默认折叠。这样既不丢失执行可解释性，也避免长工具结果和检索片段挤占正文。

| 活动 | 合并键 | 时间线中的生命周期 |
| --- | --- | --- |
| 知识库检索 | `searchId` | 每次检索一条，展示查询范围、结果数和耗时 |
| 工具调用 | `callId` | `started`、`succeeded`、`failed` 更新同一条；审批事件按 `requestId` 关联 |
| 上下文压缩 | `compactionId` | 一次真实裁剪或摘要一条，展示阶段、原因、前后 Token/字符和节省量 |

归并时按 `sequence` 去重，并按首次事件序号排序；重复回放不能产生重复活动。运行中的任务直接消费实时事件，历史任务首次展开时通过带 `types` 的活动事件查询恢复。没有活动的旧任务显示空状态，而不是编造 RAG、工具或压缩记录。

## 创建与 steer

同一用户、同一会话最多只有一个活动 Run。创建时平台锁定会话行并检查活动 Run：

- 没有活动 Run：创建新 Run、写入用户消息和首个隐式计划步骤。
- 已有活动 Run：新消息转为 steer，不再创建第二个 Run。
- 任务处于 `PAUSED` 或 `WAITING_USER` 时，steer 会把任务重新置为 `QUEUED`。
- `WAITING_USER` 时前端自动弹出补充信息输入框，从 `pendingAction.question` 恢复完整问题；提交内容走 steer 并清空待处理问题，任务中心与任务卡使用同一交互。
- `clientMessageId` 在 Run 内唯一，重复提交同一消息不会重复追加。

steer 消息先保存为 `PENDING`，在当前模型步骤结束后批量注入；应用后标记为 `APPLIED`。附件随 steer 一起保存，并在后续步骤参与上下文装配。

## 调度、租约与恢复

```text
创建 Run
  → QUEUED
  → CAS 认领并获取租约
  → RUNNING
  → 单次模型决策
  → 保存检查点
  → QUEUED / WAITING_APPROVAL / PAUSED / SUCCEEDED
```

默认调度参数：

| 配置 | 默认值 | 说明 |
| --- | ---: | --- |
| `app.ai.agent-run.enabled-types` | `*` | 允许创建 Run 的 Agent 类型；`*` 表示全部业务 Agent |
| `app.ai.agent-run.disabled-types` | 空 | 临时禁用的 Agent 类型，优先级高于启用范围 |
| `app.ai.agent-run.max-concurrency` | `4` | 单实例同时执行的 Run 数 |
| `app.ai.agent-run.dispatch-delay-ms` | `1000` | 调度扫描间隔 |
| `app.ai.agent-run.lease-seconds` | `60` | worker 租约和心跳续租时长 |

- 每个实例通过数据库条件更新认领任务，多实例不会同时执行同一个有效租约。
- worker 每隔约 15 秒发送心跳；租约过期后其他实例可以重新认领。
- 服务启动时会把心跳超时超过 `max(2 × 租约, 120 秒)` 的中断任务重新入队。
- 同一 Run 的租约连续恢复达到 3 次后标记失败，避免重复产生外部副作用。

## 计划与完成判定

Run 使用以下内部控制工具维护状态：

| 工具 | 作用 |
| --- | --- |
| `run_update_plan` | 创建或调整完整计划；步骤包含目标、验收条件、状态、摘要和证据引用 |
| `run_update_step` | 更新步骤为 `PENDING`、`RUNNING`、`DONE`、`SKIPPED` 或 `BLOCKED` |
| `run_request_user` | 仅在缺少用户才能提供的信息时进入 `WAITING_USER` |
| `run_finish` | 提交最终摘要；只有计划全部完成或明确跳过时才应调用 |

控制器不会仅凭模型声称“已完成”就结束任务。满足以下条件才进入 `SUCCEEDED`：

- 所有计划步骤为 `DONE` 或 `SKIPPED`；
- 没有待审批动作或其他等待状态；
- 报表任务已经通过 `report_finalize` 生成正式修订；
- 已形成最终答复并写入会话。

模型只输出说明性文本而没有推进计划时，控制器会追加“继续未完成步骤”的运行时指令并自动重新入队，不要求用户再次发送“继续”。连续 3 次没有推进计划则进入 `PAUSED`。

## 预算与输出截断

| 预算 | 默认值 | 达到后的行为 |
| --- | ---: | --- |
| 决策步数 | `30` | 暂停，等待用户继续 |
| 有效执行时间 | `1800` 秒 | 暂停，等待用户继续 |
| Run 总工具调用 | `80` | 暂停，保留已完成结果 |
| 单次工具结果 | `8000` 字符 | 按运行上下文预算截断并标记 |
| 累计工具结果 | `48000` 字符 | 后续结果压缩或停止继续调用 |

等待审批和等待用户不计入有效执行时间，也不持有 worker。用户对因步数或时长达到上限的任务执行“继续”时，平台按默认值追加对应预算；工具总预算不会自动追加。

Skill 的 `maxToolCalls` 继续作为单步工具上限，Run 总预算在所有步骤间累计。模型以 `finish_reason=length` 结束时，当前步骤不视为完成：

- 保留安全的部分内容作为检查点，并重试当前步骤；
- 同一章节或步骤最多自动重试 2 次；
- 连续截断后进入 `PAUSED`，原因包含 `OUTPUT_TRUNCATED`；
- 不把截断正文写入正式报表或声明任务成功。

## 上下文装配

单个模型决策只装载完成任务所需的信息：

- 用户目标、当前计划和计划修订号；
- 已完成步骤摘要和证据引用；
- 当前步骤开始后尚未应用的 steer 指令和附件；
- 最近 6 条会话消息，以及审批拒绝、失败或未知结果提示；
- 上一轮检查点中的安全摘要；
- 当前 Skill 绑定的 RAG 参考和本轮实际工具结果。

完整工具结果保留在调用审计和产物中。进入模型上下文的结果受单次、累计字符和 Token 预算约束，必要时使用压缩摘要、分页或证据引用。

## 审批与外部副作用

- 标记为只读且未被全局 `DENY` 的工具在 Run 中自动执行。
- 外部写入、发布、删除和其他 `ASK` 工具进入持久化审批。
- 审批等待默认 24 小时，不占 worker，也不消耗有效执行时间。
- 审批支持 `approved`、`approved_run` 和 `rejected`；`approved_run` 允许当前 Run 内同一精确 `tool_key` 的后续调用复用授权。
- 审批通过后 Run 重新入队；拒绝后模型基于拒绝结果调整计划，不伪造执行成功。
- 审批超时后 Run 进入 `PAUSED`，不会自动执行。
- 工具已发出但服务在记录结果前中断时，调用标记为 `UNKNOWN`，Run 暂停且禁止自动重放；需要人工确认外部系统状态后再决定是否继续。

## 报表分章节写入

报表 Run 使用平台受控工具，而不是要求模型一次输出完整文档：

| 工具 | 作用 |
| --- | --- |
| `report_prepare_document` | 创建或打开报表草稿，确定标题、格式和基础修订号 |
| `report_upsert_section` | 新增或更新单个章节 |
| `report_replace_section` | 只改写受影响章节 |
| `report_reorder_sections` | 调整章节顺序 |
| `report_finalize` | 校验草案并生成新的不可变报表修订 |

- 单章节目标约 1,200 个中文字符，硬上限 2,400 字符。
- 每次章节写入成功立即保存草稿，因此其他已完成章节不会因下一步失败而丢失。
- 修改类请求先定位受影响章节，只重写目标章节；旧的 `full_generate`、`full_rewrite` 参数继续兼容，但内部转换为章节级写入。
- 章节参数超限或被输出截断时，不提交半截内容；只缩短或拆分当前章节后重试。
- `report_finalize` 通过结构、章节完整性、证据引用和格式校验后才生成正式修订；Run 成功事件携带文档 ID、修订号和产物引用。

## 事件与断线重放

Run 事件按 `(run_id, sequence)` 唯一且只追加。`GET /runs/{runId}/events?after=<sequence>` 返回 NDJSON，客户端应保存最后成功应用的序号并从该序号续订。

主要事件：

| 事件 | 用途 |
| --- | --- |
| `run.created`、`run.snapshot` | Run 创建和完整快照 |
| `plan.updated`、`step.updated` | 计划和步骤状态变化 |
| `assistant.delta` | 当前步骤的模型文本增量 |
| `tool.started`、`tool.succeeded`、`tool.failed` | MCP 工具状态 |
| `tool.approval_required`、`tool.approval_updated` | 工具审批状态 |
| `tool.approval_executed`、`tool.approval_unavailable` | 审批后执行成功，或审批执行链路不可用 |
| `approval.required`、`approval.updated` | Run 级等待状态变化 |
| `rag.search` | 本轮知识库检索快照 |
| `context.compacted` | 一次真实发生的上下文裁剪、摘要或附件正文移除 |
| `steer.queued` | steer 已保存，等待步骤结束后应用 |
| `artifact.updated` | 报表草稿、章节或正式修订更新 |
| `run.queued`、`run.paused`、`run.resumed` | 调度和暂停状态 |
| `run.output_truncated`、`run.error` | 截断和可解释错误 |
| `run.waiting_user`、`run.succeeded`、`run.failed`、`run.canceling`、`run.cancelled` | 等待与终态事件 |

每个事件的公共字段为 `sequence`、`run_id`、`type`、`step_id`、`created_at` 和 `data`。事件流只是通知和重放通道，规则判定仍以服务端 Run 快照和状态机为准。

执行过程只需要活动事件。`GET /runs/{runId}/events` 和 `/events/list` 都支持可选的 `types` 逗号分隔过滤；省略时保持原有全量事件行为。前端固定请求 `rag.search`、`tool.started`、`tool.succeeded`、`tool.failed`、`tool.approval_*` 和 `context.compacted`。过滤结果达到 500 条时，客户端以最后一条 `sequence` 作为 `after` 继续分页，避免大量 `assistant.delta` 挤占活动窗口。

`context.compacted` 只在真实发生裁剪或摘要时写入。主要字段为 `compactionId`、`stage`、`reason`、`beforeTokens`、`afterTokens`、`savedTokens`、`beforeChars`、`afterChars`、`budgetTokens`、`budgetChars`、`omittedMessages`、`retainedMessages`、`truncatedMessages`、`omittedAttachments`、`includedAttachments` 和最多 500 字符的 `summaryPreview`。

| `stage` | 说明 |
| --- | --- |
| `run-context` | 检查点、任务提示词或近期会话超过字符/条数上限 |
| `model-input` | 当前步骤提示词超过模型输入 Token 预算 |
| `history-window` | 聊天记忆窗口裁剪，或使用摘要替代较早消息 |
| `attachment-memory` | 附件正文写入聊天记忆前被移除或压缩 |

历史 Run 不做事件回填；缺少压缩记录时前端明确提示为旧任务尚未采集该诊断。

## 运维与排障

后端日志使用 `run_id`、`step_id`、`tool_request_id` 关联。Micrometer 指标包括：

- `dih.agent.run.queue.length`
- `dih.agent.run.step.duration`
- `dih.agent.run.approval.duration`
- `dih.agent.run.recovery`
- `dih.agent.run.truncation`
- `dih.agent.run.terminal`
- `dih.agent.run.failure`

| 现象 | 检查 |
| --- | --- |
| 点击发送后仍走普通流 | Agent 类型是否在 `enabled-types` 中，以及前端是否收到 `503` 回退 |
| 一直显示等待执行 | 调度器是否启用、并发槽是否耗尽、任务是否卡在无效租约 |
| 一直显示等待审批 | 在任务中心或审批接口检查 `pendingAction.requestId`，确认未超时或被拒绝 |
| 暂停原因包含 `OUTPUT_TRUNCATED` | 缩小当前步骤或章节后点击继续；不要重放整篇报表 |
| 暂停原因包含 `UNKNOWN_TOOL_RESULT` | 先到目标外部系统核对是否已写入，再决定继续或人工修正，禁止盲目重试 |
| 页面关闭后没有继续 | 检查后端进程、Run 状态和租约恢复日志；关闭浏览器本身不应取消任务 |
| 事件重复或丢失 | 客户端按 `sequence` 去重并从最后游标重放，不要以到达顺序作为事实序号 |
| 报表没有生成修订 | 检查是否调用 `report_finalize`，以及章节、证据和格式校验是否通过 |
