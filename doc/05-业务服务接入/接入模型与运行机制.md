# 接入模型与运行机制

业务服务接入以“服务、实例、心跳、事件”为核心模型。接入方负责生成稳定身份并持续上报，ZenVis 负责保存最新实例状态、计算有效状态、记录事件并提供只读查询。

## 服务与实例身份

一个业务服务可以同时运行多个实例。ZenVis 使用 `service_code + instance_id` 唯一确定一个实例。

| 字段 | 含义 | 建议 |
| --- | --- | --- |
| `service_code` | 业务服务的稳定编码 | 同一服务的所有实例保持一致，例如 `order-api` |
| `service_name` | 面向用户的展示名称 | 使用清晰、稳定的业务名称，例如“订单服务” |
| `instance_id` | 单个运行实例的唯一标识 | 同时运行的实例不能重复，并应在预期生命周期内稳定 |
| `environment` | 部署环境 | 建议统一使用 `dev`、`test`、`staging`、`prod` 等约定 |
| `version` | 应用版本 | 建议使用可追溯的发布版本或构建版本 |

如果容器主机名每次重建都会变化，由主机名推导的 `instance_id` 也会变化，ZenVis 会将其展示为一个新实例。需要连续追踪同一逻辑实例时，应显式配置稳定且唯一的实例标识。

## 心跳注册

业务应用不需要先在 ZenVis 中手工创建实例。首次成功心跳会自动注册实例，后续心跳更新该实例的最新状态和信息。

心跳主要包含：

- 服务与实例身份；
- 主动上报状态及说明；
- 版本、环境、主机、端口和管理地址；
- 客户端心跳时间；
- 可选的实例扩展元数据。

ZenVis 使用服务器实际接收心跳的时间判断在线状态。客户端提供的 `heartbeat_time` 只用于展示，不能延长在线时间。因此应保证网络可达和上报频率，而不能依赖修改客户端时间维持在线。

## 上报状态与有效状态

业务应用可以主动上报三种状态：

| 上报状态 | 含义 |
| --- | --- |
| `UP` | 实例正常运行 |
| `DEGRADED` | 实例仍在运行，但部分能力降级 |
| `DOWN` | 实例主动声明已下线或正在停止 |

管理页面还会显示 ZenVis 计算出的 `OFFLINE`：

| 条件 | 有效状态 |
| --- | --- |
| 最后心跳未超过离线阈值，且上报 `UP` | `UP` |
| 最后心跳未超过离线阈值，且上报 `DEGRADED` | `DEGRADED` |
| 最后心跳未超过离线阈值，且上报 `DOWN` | `DOWN` |
| 最后心跳早于当前服务器时间减离线阈值 | `OFFLINE` |

默认心跳间隔为 30 秒，默认离线阈值为 90 秒。最后心跳恰好位于阈值边界时仍显示主动上报状态，超过边界后才显示 `OFFLINE`。

正常关闭时可以主动上报 `DOWN`，但强制终止、进程崩溃或网络中断可能来不及执行关闭逻辑。运行监测必须同时依赖心跳超时，不能只依赖 `DOWN`。

## 事件上报顺序

事件用于记录启动、停止、异常和重要业务变化。事件所属实例必须至少成功上报过一次心跳：

1. 应用生成服务和实例身份。
2. 应用发送首次心跳，ZenVis 注册实例。
3. 应用上报启动事件和自定义事件。
4. 应用持续发送心跳。
5. 正常关闭时上报停止事件和 `DOWN` 心跳。

未注册实例直接上报事件时，服务端返回业务状态 `404`。已经注册但当前显示为 `OFFLINE` 的实例仍可以上报事件；新事件不会代替心跳，也不会改变实例的在线判定。

## 事件级别与内容

事件严重级别支持：

- `INFO`：正常生命周期或一般业务信息；
- `WARN`：需要关注但业务仍可继续；
- `ERROR`：明确失败，通常需要排查或重试；
- `CRITICAL`：影响核心能力或需要立即处理。

建议使用稳定、可筛选的 `event_type`，例如 `ORDER_SYNC_FAILED`，并在 `trace_id` 中携带已有的链路标识。`message` 和扩展 `data` 不应包含密码、Token、完整个人敏感信息或无边界的大对象。

## 时间语义

公开接口中的时间字符串使用：

```text
yyyy-MM-dd HH:mm:ss
```

心跳涉及两个不同时间：

- `heartbeat_time`：客户端生成的报告时间，只用于展示；
- `received_at`：ZenVis 接收时间，用于在线判断和保留策略。

事件也包含两个时间：

- `occurred_at`：客户端报告的事件发生时间，用于展示和条件查询；未提供时使用接收时间；
- `accepted_at` 或记录创建时间：ZenVis 接受事件的时间，用于确认接收和数据保留。

跨时区部署时，接入方应统一约定业务时区。Starter 默认按 `Asia/Shanghai` 格式化上报时间，可通过配置修改。

## 幂等与重复上报

事件使用 `event_id` 幂等接收：

- 同一 `service_code + instance_id` 重复上报相同 `event_id`，服务端返回首次保存的记录，并标记为重复；
- 相同 `event_id` 已属于其他服务实例时，服务端返回业务状态 `409`；
- REST 接入方重试时必须复用原 `event_id`，不能每次生成新 ID；
- Starter 为自定义事件生成 UUID，并在单次进程生命周期内为启动和停止事件保留固定 ID。

心跳不需要单独的幂等键，同一服务实例的后续心跳持续更新最新状态。

## 数据保留

默认情况下：

- 事件记录保留 30 天；
- 长期离线实例保留 30 天；
- 清理任务每小时执行一次；
- 实例仍存在近期事件时，不会被提前清理。

具体值由 ZenVis 服务端配置控制，生产设置见[生产部署与验收](/05-业务服务接入/生产部署与验收.md)。
