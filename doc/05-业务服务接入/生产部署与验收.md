# 生产部署与验收

生产接入需要同时考虑网络暴露、身份稳定性、状态时效、事件可靠性、数据保留和故障排查。本页适用于 Starter 和 REST API 两种接入方式。

## 网络与安全

业务服务的两个上报端点不要求 ZenVis Session 或普通 API Bearer Token，也没有内置应用签名和限流。生产环境应在外围完成：

- 仅通过 HTTPS 或可信服务网络传输；
- 使用 API 网关、反向代理或防火墙限制来源；
- 按来源、服务和接口设置限流，避免异常实例压垮后端；
- 不直接向互联网暴露 ZenVis 后端管理端口；
- 对管理查询继续执行 Session 或 Bearer Token 认证；
- 控制 `metadata`、事件标题、消息和 `data` 中的敏感信息；
- 日志只记录事件标识和失败原因，不记录真实凭据或完整敏感载荷。

如果部署侧增加了签名或其他鉴权，应由网关或接入客户端共同实现，并保持 ZenVis 后端两个公开路径的内部调用契约不变。

## 地址与代理

Starter 的 `zenvis.business-service.base-url` 和 REST 客户端使用的是 ZenVis 后端根地址，不要在末尾追加 `/api/v1`。

常见示例：

```properties
# 业务服务可以直接访问后端
zenvis.business-service.base-url=http://zenvis-backend:11001

# 通过生产网关访问
zenvis.business-service.base-url=https://zenvis.example.com
```

浏览器访问管理页面时通常经过前端 `/zenvis` 代理，但业务服务是否需要该前缀取决于生产网关配置。上线前应从业务应用所在网络实际调用心跳端点验证，不要只在浏览器所在网络测试。

## 心跳和离线阈值

服务端配置如下：

| 配置 | 环境变量 | 默认值 | 说明 |
| --- | --- | ---: | --- |
| `app.business-service.offline-threshold-seconds` | `APP_BUSINESS_SERVICE_OFFLINE_THRESHOLD_SECONDS` | `90` | 心跳离线阈值，秒 |
| `app.business-service.event-retention-days` | `APP_BUSINESS_SERVICE_EVENT_RETENTION_DAYS` | `30` | 事件保留天数 |
| `app.business-service.instance-retention-days` | `APP_BUSINESS_SERVICE_INSTANCE_RETENTION_DAYS` | `30` | 长期离线实例保留天数 |
| `app.business-service.cleanup-delay-ms` | `APP_BUSINESS_SERVICE_CLEANUP_DELAY_MS` | `3600000` | 清理任务间隔，毫秒 |

心跳间隔应显著小于离线阈值。默认 30 秒心跳与 90 秒阈值允许短时网络抖动，但不能容忍持续超过 90 秒的不可达。

调整时应同时考虑：

- 网络延迟和偶发失败；
- 实例规模与心跳请求总量；
- 业务对离线发现速度的要求；
- 应用暂停、GC、节点迁移和滚动发布可能造成的抖动。

不要把阈值设得与心跳间隔相同。通常至少保留两个以上的补报机会。

## 身份与发布策略

上线前确认：

- 同一业务服务的所有实例使用相同 `service_code`；
- 并发实例的 `instance_id` 互不重复；
- 容器重建是否应该生成新实例记录符合运维预期；
- `environment` 能区分生产、测试等环境；
- `version` 能关联到实际发布构件；
- `management_url` 仅在访问方具备相应权限时提供；
- `metadata` 使用稳定、有限的键，不放入高频变化或大体积内容。

滚动发布期间，新旧版本实例可能同时存在，这是正常现象。旧实例应通过 `DOWN` 或心跳超时退出，新实例通过首次心跳自动注册。

## 事件可靠性

ZenVis 业务事件用于观测，不应成为核心业务事务的唯一记录：

- Starter 的事件队列位于进程内，队列满或进程退出时可能丢失；
- REST 客户端一次请求成功前不能假定事件已保存；
- 关键事件应先写入业务数据库、事务消息或可靠消息队列；
- 重试必须复用原 `event_id`；
- 应限制重试次数、退避间隔和本地积压，避免恢复后形成请求风暴；
- 心跳应独立于事件积压，不能因为重放事件而停止。

对于只用于辅助排查的一般事件，可以接受尽力上报；对于审计、计费、订单状态等关键事实，应以业务系统的权威数据为准。

## 数据容量和保留

单次心跳 `metadata` 的 UTF-8 JSON 不超过 16 KiB，单次事件 `data` 不超过 64 KiB。事件类型、标题、消息和 Trace ID 还有各自长度限制，完整约束见[业务服务 REST API](/08-API参考/RestfulAPI/业务服务.md)。

清理任务先删除超过事件保留期的事件，再删除最后心跳和最后事件接收时间均超过实例保留期的实例。近期事件会阻止实例被提前清理。

生产保留期应结合事件量、数据库容量、审计要求和外部归档策略确定。ZenVis 的事件保留不能替代业务系统自己的合规归档。

## 上线验收

### 基础接入

1. 启动一个测试实例。
2. 登录 ZenVis，进入“服务管理 → 业务应用服务”。
3. 在一个心跳周期内确认服务和实例出现。
4. 核对服务编码、实例标识、版本、环境、主机和端口。
5. 等待两个心跳周期，确认最后心跳持续更新。

### 状态与生命周期

1. 正常运行时确认有效状态为 `UP`。
2. 测试降级场景时确认可以上报并展示 `DEGRADED`。
3. 正常关闭应用，确认停止事件和 `DOWN` 心跳。
4. 强制停止测试实例，确认超过离线阈值后显示 `OFFLINE`。
5. 重启应用，确认新实例或原实例身份符合发布策略。

### 事件

1. 上报包含事件类型、级别、标题、Trace ID 和扩展数据的测试事件。
2. 按服务、实例、级别和时间检索该事件。
3. 使用相同 `event_id` 重试，确认没有生成重复记录。
4. 对关键事件验证业务侧持久化和补偿流程。

### 故障与安全

1. 临时阻断 ZenVis 网络，确认宿主业务请求仍正常。
2. 恢复网络，确认心跳重新出现。
3. 验证连接和读取超时不会长期占用业务线程。
4. 验证非允许来源无法访问公开上报端点。
5. 验证网关限流、TLS 证书和日志脱敏配置。

## 常见故障排查

### 服务没有出现在 ZenVis

- 检查地址是否为后端根地址，且没有错误追加 `/api/v1`；
- 从业务应用实际运行环境测试心跳端点，而不是只在本机浏览器测试；
- 检查网关、防火墙、DNS、代理和 TLS 证书；
- Starter 检查是否误设 `zenvis.business-service.enabled=false`；
- 同时检查 HTTP 状态码和响应中的业务 `status`。

### 实例频繁新增

通常是 `instance_id` 随主机名、容器名或端口变化。显式配置稳定实例 ID，或确认每次重建生成新实例正是预期策略。

### 多个实例互相覆盖

多个并发实例使用了相同的 `service_code + instance_id`。为每个实例注入唯一标识，不能只使用服务名称作为实例 ID。

### 实例显示 OFFLINE

- 检查最后心跳接收时间，而不是只看客户端时间；
- 核对心跳间隔是否显著小于离线阈值；
- 检查应用暂停、线程阻塞、网络抖动和网关限流；
- 确认服务器时间正常。

### 自定义事件没有出现

- 确认实例已经至少成功发送过一次心跳；
- 检查队列是否已满、组件是否正在停止以及网络是否可达；
- 检查事件字段、扩展数据大小和响应业务状态；
- Starter 事件为尽力上报，关键事件应检查业务侧持久化或补偿记录。

### 正常关闭后仍未显示 DOWN

强制终止、`SIGKILL` 或关闭窗口过短会跳过最后上报。该场景最终应由心跳超时转为 `OFFLINE`，不能假设所有退出都能发送 `DOWN`。
