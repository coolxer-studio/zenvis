# 插件与扩展架构

ZenVis 插件把数据模型、接入任务、动态 API、页面、看板、MCP、Skill 和菜单封装为一个可安装单元。本文描述运行时契约和生命周期；具体开发步骤由[插件开发与集成](/03-插件开发与集成/README.md)承载。

## 扩展面

```text
插件包
  ├── 文档与 RAG
  ├── Meta 与 ClickHouse Schema
  ├── Vectum 推送任务
  ├── 动态 REST API 与 MySQL 迁移
  ├── 低代码 / HTML UI
  ├── 看板
  ├── 外部 MCP Server 描述
  ├── 运行时 Skill
  └── 菜单
          │
          ▼
PluginService
  校验 → 安装 → 加载 → 升级/恢复 → 卸载
```

平台功能优先通过这些稳定扩展面实现。只有需要通用运行机制时才修改后端内核，具体业务域逻辑应留在插件中。

## 插件目录契约

| 目录 | 运行时内容 | 主要消费者 |
| --- | --- | --- |
| `00_doc` | README、业务文档和附件 | 插件管理、RAG |
| `01_meta` | 实体、属性、操作符和数据样例 | Meta、ClickHouse Schema、Retrieval |
| `02_push-task` | Source、Transform、Sink 任务 | Vectum、数据接入 |
| `03_api` | 单个动态 API JAR、MySQL 迁移 | 动态类加载器、迁移服务 |
| `04_ui` | 低代码应用、单页配置和静态页面 | 前端页面容器、静态资源服务 |
| `05_dashboard` | 看板配置和 HTML 页面 | Dashboard、前端看板 |
| `06_mcp` | 外部 MCP Server 配置 | MCP Client 注册表 |
| `07_skill` | `skill.json`、提示词和资源 | Skill Registry、业务 Agent |
| `08_menu` | 菜单树、页面类型和权限入口 | 菜单与角色权限 |

目录按能力可选，但已提供的目录必须符合平台 Schema。插件索引负责声明包名、版本、标题、图标和各能力入口。

## 仓库边界

| 位置 | 职责 |
| --- | --- |
| `zenvis-plugin` | 平台内置插件和公共 API 依赖 |
| `zenvis-plugin-community` | 社区或客户场景插件 |
| `agent-skills/create-zenvis-plugin` | 研发侧生成、校验和打包工作流 |
| 后端插件安装目录 | 已上传并由平台管理的运行时插件 |

内置与社区插件使用同一运行契约。研发 Skill 只帮助创建插件，不会进入 `07_skill` 注册表，也不会被后端安装器扫描。

## 安装流程

```text
上传归档
  → 解压到隔离工作区
  → 校验路径、文件类型、包名、版本和目录结构
  → 解析候选插件
  → 校验 Meta、迁移和各类配置
  → 按阶段安装 00_doc ... 08_menu
  → 注册插件记录与资源关系
  → 加载动态 API
  → 读回并确认 INSTALLED
```

安装必须防止归档路径穿越，不能把文件写出插件根目录。发布包应排除源码、构建缓存、历史归档、日志和非必要样本。

## 动态 API

`03_api` 最多包含一个运行 JAR。`ExtendJarManager` 为每个插件创建和持有独立加载器：

```text
Plugin API JAR
  → ExtendJarClassLoader（每个插件独立）
  → ClassGraph 扫描 Controller
  → Registrar 注册 Spring Bean
  → ExtendJarHandlerMapping 注册路由
```

卸载或升级时由 Cleaner 注销路由和 Bean，再关闭对应 ClassLoader。插件类必须使用唯一包名和 Bean 名，不能覆盖平台 Controller。

动态 API 的稳定依赖面包括 Spring Web、公开 DTO/VO、插件公共 API 和已声明的数据源访问方式。插件不得引用后端内部 Entity、Repository、Service 实现或工具类，否则平台升级会破坏二进制兼容。

## 数据库迁移

### MySQL

插件迁移采用版本化、只向前策略：

- 文件按版本排序执行。
- 历史表记录插件包名、版本、描述和 SHA-256。
- 已执行版本必须保留相同内容，校验和变化会阻止升级。
- 新版本只能追加迁移，不能重写旧文件。
- 迁移失败时插件升级停止并保留恢复状态。

### ClickHouse

ClickHouse 结构来自 Meta，升级以新增式变更为主。新增表和字段可以自动应用；删除、重命名和不兼容类型变更不能通过重建表静默完成。

卸载插件会清理插件关联的 ClickHouse 表和数据，因此属于高风险动作；MySQL 迁移历史保留，用于后续审计和重新安装判断。

## 升级与恢复

升级不是简单覆盖目录：

```text
读取当前插件
  → 创建持久化快照
  → 校验候选包和迁移
  → 记录升级阶段
  → 逐能力应用候选内容
  → 重载 Meta、Schema、API 和运行资源
  → 成功后切换版本
```

如果进程在升级中断，下一次启动会在加载全局 Meta 和插件 API 之前执行恢复。恢复依赖持久化快照和阶段记录，不能只依赖内存状态。

升级要保护已有业务数据：

- MySQL 迁移只向前执行。
- ClickHouse 使用兼容的增量结构变更。
- 旧 API 在新 API 成功加载前不应提前失效。
- 配置、菜单、看板和文档按插件资源关系更新。
- 失败时恢复可恢复资源，并保留可诊断日志。

## 卸载边界

卸载按资源归属反向清理：

- 注销动态 API、Bean 和 ClassLoader。
- 移除菜单、看板、UI、推送任务、MCP 和 Skill。
- 从 RAG 中清理该插件文档来源。
- 移除 Meta 并重新建立有效快照。
- 删除插件声明的 ClickHouse 表和数据。
- 保留平台需要的迁移历史和审计信息。

卸载前必须明确数据影响，不能把停用或临时下线替代成卸载。

## 配置与页面

- 低代码应用由 `site.json` 组织多个页面。
- 单页面应用由 `index.json` 提供页面配置。
- HTML 页面通过后端 `/html-page/**` 提供静态资源。
- 菜单只引用插件内配置、相对路径或允许的外部地址。
- 看板和页面引用逻辑实体与属性，不绑定 ClickHouse 物理列。

配置、看板和菜单可以由数据可视化 Agent 通过受控 MCP Tool 创建，但写操作仍经过审批和读回校验。

## MCP 与 Skill

`06_mcp` 描述插件依赖的外部 MCP Server；`07_skill` 描述运行时业务 Skill。二者可以组合，但职责不同：

| 能力 | MCP | Skill |
| --- | --- | --- |
| 主要内容 | 服务连接和可发现工具 | 提示词、业务上下文和工具 allowlist |
| 注册位置 | MCP Client Registry | Skill Registry |
| 权限边界 | 全局策略、Agent scope、审批 | Skill allowlist 与 Agent 类型 |
| 是否包含执行代码 | 外部服务提供 | 通常不直接执行代码 |

外部 MCP 工具在运行期动态发现，插件文档只声明连接和使用边界，不静态复制全部工具 Schema。

## 架构检查

- 插件包名、目录和索引一致。
- Meta、推送字段和 ClickHouse 目标字段一致。
- 动态 API 只有一个运行 JAR，且不引用后端内部实现。
- MySQL 迁移版本不可变，升级包只追加。
- 页面、看板和菜单使用逻辑名称与安全 URL。
- 文档、MCP、Skill 和菜单随生命周期同步清理或恢复。
- 安装、升级和卸载均有明确日志与最终状态。
