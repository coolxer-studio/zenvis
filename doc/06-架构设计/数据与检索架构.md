# 数据与检索架构

本文统一说明 ZenVis 的数据存储职责、数据接入链路、Meta 模型、Retrieval 查询引擎、过滤器兼容和结构演进边界。

## 数据职责

| 组件 | 主要数据 | 访问方式 | 一致性边界 |
| --- | --- | --- | --- |
| MySQL | 用户、角色、菜单、插件、配置索引、过滤器、会话、任务、MCP 策略与审计 | JPA、JDBC | 平台事务与生命周期状态 |
| ClickHouse | 插件声明的分析实体、事件和指标 | JPA、原生查询、受控查询引擎 | 大规模检索、聚合和实体 CRUD |
| Redis | HTTP Session、审计用户缓存和短期运行状态 | Spring Data Redis | 会话与快速状态 |
| Redis Stack | RAG 文档、Embedding 和向量索引 | Spring AI Redis Vector Store | 相似度召回 |
| Kafka | 原始消息、转换链路和死信 | Vectum Source/Sink | 数据接入解耦与缓冲 |
| Vectum | Source、Transform、Sink 任务和运行工作区 | 独立服务 | 采集、校验、转换和写入 |

MySQL 与 ClickHouse 是两个显式数据源，分别具有独立的 EntityManagerFactory 和事务管理器。插件 MySQL 迁移使用专用 JDBC Template，不能误用 ClickHouse 主数据源。

## 数据流全景

```text
外部数据源
    │
    ▼
Vectum Source
    │
    ▼
Kafka 原始主题
    │
    ├── 校验失败 ──→ DLQ / 运行日志
    │
    ▼
Transform
    │
    ▼
ClickHouse Sink ──→ 分析实体表
                         │
Meta 配置 ───────────────┤
                         ▼
             Retrieval / Entity Analytics
                         │
                         ▼
               REST / MCP / 页面与看板
```

Meta 业务属性、Transform 输出字段和 ClickHouse Sink 字段必须一致。Kafka 与 Vectum 负责传输和转换，ZenVis Meta 负责逻辑模型，ClickHouse 负责最终分析存储。

## Meta 模型

Meta 默认从 `app.paths.retrieval.metadata` 指定目录加载。多个 JSON 文件先合并、完整校验，再以不可变快照一次性替换当前运行配置。

### 核心对象

| 对象 | 主要职责 |
| --- | --- |
| `entity` | 定义逻辑实体、物理表、数据源和默认排序 |
| `attribute` | 定义逻辑属性、物理列、类型、展示、复制、链接和操作符 |
| `operator` | 定义可用于条件编辑和查询生成的操作符 |
| 查询请求 | 描述实体、条件、展示字段、分页和排序 |
| Retrieval 规则 | 在 MySQL 保存可复用的逻辑查询配置 |

接口、规则和前端状态只使用逻辑 `entity.name` 与 `attribute.name`。`table_name`、`column_name` 只在后端数据层使用，不能泄露成前端稳定契约。

### 原子加载

```text
读取全部 Meta 文件
  → 合并实体、属性和操作符
  → 校验名称、ID、引用、类型和链接模板
  → 构造不可变快照
  → 原子替换当前快照
  → 依据新快照执行 ClickHouse 增量结构同步
```

任何文件读取或整体校验失败时，系统继续使用上一份有效快照。请求只绑定一个完整快照，不会看到加载到一半的状态。

### 平台保留属性

每个实体运行时补充两个平台属性，业务 Meta 不需要重复声明：

| 属性 | ClickHouse 类型 | 用途 |
| --- | --- | --- |
| `zenvis_id` | `Nullable(UUID)` | 新记录的平台标识，支持详情、更新和删除 |
| `zenvis_insert_time` | `DateTime64(3)` | 平台写入时间和默认趋势统计时间 |

两者默认不展示。已有表升级时，历史记录的 `zenvis_id` 可以为空，因此历史数据仍可查询，但不能通过新平台 ID 执行实体写操作。

## Retrieval 模块定位

Retrieval 是 Meta 驱动的单实体受控查询模块，提供普通条件、高级表达式、展示列、分页、排序和个人过滤器。

当前边界：

- 一次请求只查询一个实体，不支持跨实体 Join。
- 展示实体必须与检索实体一致。
- 普通条件和高级表达式最终都转换为受控条件树。
- 不提供自由 SQL、函数、子查询、注释或多语句执行入口。
- 过滤器按创建用户隔离。
- 当前没有实体级、字段级或行级授权模型；`RetrievalAccessPolicy` 是预留扩展点。

## 查询链路

```text
retrieval/index.vue
  ├── filter.vue：实体、条件、高级表达式
  └── table.vue：展示列、分页、排序
          │
          ▼
POST /api/v1/retrieval/do
          │
          ▼
RetrievalController
          │
          ▼
RetrievalServiceImpl / RetrievalRuleServiceImpl
  请求校验 → 表达式解析 → 绑定 Meta 快照
          │
          ▼
DataQueryServiceImpl
  构造查询上下文和逻辑/物理字段映射
          │
          ▼
QueryEngineImpl
  生成受控 ClickHouse 查询 → 分页/排序 → 逻辑字段结果
```

响应记录以逻辑属性名作为键。前端不得根据物理表结构自行拼接查询，也不得通过插件页面绕过 Retrieval 校验。

## 查询约束

| 项目 | 当前约束 |
| --- | --- |
| 实体 | 必须存在且每次只能一个 |
| 普通条件 | 最多 50 个，组合逻辑为 `and` 或 `or` |
| 条件值 | 单条件最多 200 个，单值最长 2 KiB |
| 展示字段 | 1–100 个，不得重复 |
| 排序 | 字段必须属于当前实体，方向为 `asc` 或 `desc` |
| 分页 | `page >= 1`，`size` 为 1–200 |
| 高级表达式 | 最长 8 KiB、最多 50 个条件、最多 10 层括号 |
| 时间 | 按 `app.retrieval.time-zone` 解释，默认 `Asia/Shanghai` |

高级表达式支持受限的比较、模糊、范围、集合和空值操作。`WhereExpressionParser` 每次解析都创建独立状态，解析游标和条件计数不能放入 Spring 单例字段。

## 过滤器生命周期

### V2 存储

新建或更新后的 `rule_string` 使用 `schema_version: 2`，只保存逻辑配置：

```json
{
  "schema_version": 2,
  "type": "normal",
  "entity": "asset",
  "criteria_logic": "and",
  "criteria_list": [],
  "display_list": [
    {
      "entity": "asset",
      "attribute_list": ["ip", "device_name"]
    }
  ],
  "page": 1,
  "size": 20,
  "sort_by": "device_name",
  "order": "asc"
}
```

规则不复制完整 Meta。每次详情或执行都绑定当前快照，因此字段删除、改名或操作符变化后会返回失效项，而不是继续执行旧物理结构。

### 兼容策略

- 继续读取历史 compact/expanded 规则 JSON。
- 读取旧规则时不自动修改数据库。
- 旧规则成功更新后写为 V2。
- 含自由 SQL 的历史规则标记为 `LEGACY_SQL_DISABLED`，只允许查看、修正或删除。
- 元数据变化导致的失效规则不会自动执行。
- 不进行破坏性批量迁移，发布前只读统计旧格式和失效原因。

### 归属隔离

列表、详情、更新、删除和按规则执行都绑定 `create_by = 当前用户`。不存在和越权统一返回规则不可用，避免通过 ID 枚举其他用户数据。MCP 规则工具复用同一用户上下文和归属校验。

## 实体查询与分析

实体能力与 Retrieval 共用同一 Meta：

```text
Meta
 ├── Retrieval：条件查询与个人规则
 ├── EntityCore：列表、详情、新增、更新、删除
 └── EntityAnalytics：计数、分组、趋势、分布和关系分析
```

实体 API 和 MCP Tool 都接受逻辑实体与属性名。数据可视化 Agent 只使用允许的实体分析工具，不执行任意 SQL，也不进行实体写入。

## 链接与展示字段

`link_template` 使用当前实体逻辑属性作为占位符，例如 `/asset/detail?id={zenvis_id}`。后端负责提供模板需要的隐藏字段，前端只对当前行实际存在的值进行 URL 编码和安全检查。

模板目标仅允许相对地址或 `http/https`。字段缺失、值为空、占位符非法或目标协议不安全时，单元格退化为普通文本。

## 结构演进

### MySQL

- 平台表由平台初始化和代码版本维护。
- 插件业务表通过版本化迁移文件演进。
- 已执行迁移记录版本与 SHA-256，禁止同版本改写。
- Spring AI Chat Memory 明确使用 MySQL 数据源。

### ClickHouse

- 初始化 SQL 只在首次启动执行并写入标记。
- Meta 驱动的实体结构使用新增式变更。
- 插件升级不得通过删除重建表破坏业务数据。
- 平台保留字段迁移失败时中止启动，避免继续写入不完整结构。

### Redis 与向量索引

- Redis Session 与 Redis Stack 向量存储是两个不同职责。
- RAG 索引可按配置关闭、初始化或重建。
- 向量文档按来源和元数据区分，删除插件文档时只清理对应来源。

## 观测与排障边界

- INFO 日志记录查询上下文、实体、条件数、字段数和耗时。
- 生成查询只在 DEBUG 输出，值、Token 和敏感请求字段需要脱敏。
- Meta reload 失败必须记录具体文件和原因，并保留旧快照。
- 规则失效、越权拒绝和表达式解析错误应分别统计。
- 数据接入同时检查 Vectum 运行日志、Kafka 主题、DLQ 和 ClickHouse 目标表。
