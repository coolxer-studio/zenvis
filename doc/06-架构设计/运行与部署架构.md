# 运行与部署架构

本文依据当前 `deploy/docker-compose.yml` 说明 ZenVis 的服务拓扑、健康依赖、配置挂载、持久化边界和本地开发关系。

## Compose 拓扑

```text
                    Browser / External Client
                              │
                              ▼
                  zenvis-frontend :11000
                         Nginx + SPA
                              │
                              ▼
                   zenvis-backend :11001
          ┌───────────────┬───────┴────────┬──────────────┐
          ▼               ▼                ▼              ▼
    mysql-service   clickhouse-service  redis-service  redis-stack-service
       :3306          :8123/:9000         :6379           :16379

    Data Source → vectum-service :11002 → kafka-service :9094 → ClickHouse
```

所有容器加入 `zenvis-network`。服务间访问使用 Compose 服务名和容器端口，宿主机开发工具使用映射端口。

## 服务职责

| 服务 | 宿主机入口 | 职责 | 主要持久化 |
| --- | --- | --- | --- |
| `zenvis-frontend` | `11000` | Nginx 静态站点和后端反向代理 | 前端 Nginx 配置 |
| `zenvis-backend` | `11001` | REST、MCP、Meta、插件、DIH 和平台管理 | 开放配置、插件和运行文件 |
| `mysql-service` | `3306` | 平台事务、配置、会话、任务和审计 | `deploy/data/mysql/data` |
| `clickhouse-service` | `8123`、`9000`、`9009` | 分析实体、事件和聚合数据 | 数据目录与日志目录 |
| `redis-service` | `6379` | Session、缓存和运行状态 | `deploy/data/redis/data` |
| `redis-stack-service` | `16379` | RAG 文档和向量索引 | `deploy/data/redis-stack/data` |
| `kafka-service` | `9094` | 数据接入消息、转换缓冲和死信 | Kafka 日志目录 |
| `vectum-service` | `11002` | Source、Transform、Sink 任务 | 工作区与 Vector 状态 |

端口是当前 Compose 默认值，实际生产环境可以通过网关、端口映射和环境变量调整。业务代码不能把宿主机地址写成稳定依赖。

## 启动依赖

### 平台主链路

```text
MySQL ───────────┐
ClickHouse ──────┤
Redis ───────────┼─ healthcheck 通过 ─→ ZenVis Backend ─→ ZenVis Frontend
Redis Stack ─────┘
```

后端通过 `depends_on.condition: service_healthy` 等待四个核心存储。前端依赖后端容器启动，并通过自己的健康检查验证站点。

Kafka 和 Vectum 属于数据接入链路，没有被定义为后端启动的强依赖。它们异常时平台基础管理和已有数据查询仍可运行，但新增数据接入、推送任务或演示链路会失败。

### 后端内部初始化

容器健康并不等于业务初始化完成。后端启动后还会执行：

1. 平台基础数据初始化。
2. MySQL、ClickHouse 首次脚本。
3. 插件升级恢复。
4. Meta 加载和 ClickHouse 增量 Schema。
5. 已安装插件动态 API 加载。
6. RAG、MCP Client、任务调度等条件化组件初始化。

生产探针应使用应用健康端点，并结合初始化日志判断是否达到可服务状态。

## 健康检查

| 类型 | 检查目标 |
| --- | --- |
| Kafka | Broker 可响应 |
| Redis / Redis Stack | `PING` 可用 |
| MySQL | 数据库连接和查询可用 |
| ClickHouse | HTTP 或客户端查询可用 |
| Backend | Actuator 健康状态 |
| Frontend | Nginx 页面可访问 |
| Vectum | 服务健康接口 |

健康检查用于控制启动顺序和故障识别，不替代业务验收。数据库健康不代表 Meta、插件、向量索引或数据推送任务已经完成初始化。

## 配置层次

```text
镜像内默认配置
  < application-{profile}.properties
  < 挂载的 application.properties
  < 环境变量
```

后端主要配置域：

| 配置前缀 | 内容 |
| --- | --- |
| `spring.datasource.mysql.*` | MySQL 数据源 |
| `spring.datasource.clickhouse.*` | ClickHouse 数据源 |
| `spring.data.redis.*` | Session Redis |
| `spring.ai.vectorstore.redis.*` | Redis Stack 向量存储 |
| `spring.ai.openai.*` | OpenAI 兼容模型和 Embedding |
| `spring.ai.mcp.server.*` | MCP Server 端点和能力 |
| `app.paths.*` | 配置、插件、Meta、Skill、HTML 和会话工作区 |
| `app.security.*` | REST 与 MCP Bearer Token |
| `app.ai.*` | Agent、MCP、上下文、任务和工具预算 |
| `app.business-service.*` | 离线阈值和数据保留 |

敏感配置通过环境变量或受控密钥系统注入。文档、Compose 示例、前端静态资源和插件归档不应复制生产凭据。

## 开放配置与挂载

后端容器挂载：

- `deploy/config/zenvis-backend/config/application.properties`：运行配置。
- `deploy/open_config`：Meta、页面、菜单、Agent 和其他开放配置。

前端容器挂载 Nginx `conf.d`，负责静态资源、SPA 回退和 API 代理。数据库、Redis、Kafka 和 Vectum 分别挂载配置与数据目录。

开放配置属于运行输入，不是临时缓存。修改前应校验格式和 Schema，并根据配置类型执行对应的 apply/reload 动作。

## 持久化与备份

| 数据 | 备份重点 |
| --- | --- |
| MySQL | 平台表、过滤器、插件状态、会话、任务和审计 |
| ClickHouse | 插件实体表和分析数据 |
| Redis | Session 通常可重建；按业务需求决定持久化级别 |
| Redis Stack | 向量索引可从原文重建，但重建有成本 |
| 插件目录 | 已安装包、升级快照和运行资源 |
| 开放配置 | Meta、页面、菜单、Agent 和系统配置 |
| Vectum 工作区 | 任务配置、运行状态和采集位点 |

恢复顺序应先恢复持久化数据和配置，再启动后端执行结构检查，最后启动前端与数据接入任务。

## 本地开发模式

本地开发通常只通过 Compose 启动基础设施，前后端在宿主机运行：

```text
Compose：MySQL + ClickHouse + Redis + Redis Stack + Kafka + Vectum
Host：zenvis-backend（Maven）
Host：zenvis-frontend（Vite）
```

- 后端开发 Profile 使用宿主机映射端口连接基础设施。
- 前端 Vite 通过 `VITE_BASE_URL` 或代理连接后端。
- 插件 API 在插件仓库构建后安装到运行实例。
- 不要同时启动占用相同端口的容器版和宿主机版服务。

具体命令见 [deploy 开发对接指南](/07-开发指南/deploy-开发对接指南.md)。

## 故障隔离

- MySQL 不可用：平台认证、配置、会话和大多数管理功能不可用。
- ClickHouse 不可用：检索、实体分析和数据写入不可用，平台配置仍可能可读。
- Redis 不可用：Session 和部分运行状态失效。
- Redis Stack 不可用：RAG 和向量管理失效，非 RAG 功能可以继续。
- Kafka 或 Vectum 不可用：数据接入中断，已有 ClickHouse 数据仍可查询。
- 模型服务不可用：AI 会话和 Agent 失败，非 AI 平台能力不受影响。
- 外部 MCP 不可用：依赖该 Server 的工具不可用，本地工具和其他 Server 不应被连带禁用。

## 生产边界

- 只向必要网络暴露端口，数据库和中间件优先保留在内部网络。
- 修改镜像或配置后依次验证存储、后端、前端、数据接入和 AI 能力。
- 升级前备份 MySQL、ClickHouse、开放配置和插件目录。
- 不通过删除数据目录解决迁移错误。
- 日志、健康检查和业务审计使用不同的保留策略。
- 多架构镜像由 `ARCH` 选择，镜像标签与部署节点架构必须一致。
