# 数据推送 MCP 工具

`PushTaskMcpTool` 注册 11 个数据推送任务工具，覆盖查询、详情、日志、诊断、校验和完整生命周期。查询工具默认可读取 `SYSTEM`、`MCP`、`API`、`WEB` 全部来源；创建、更新、启停和删除继续接受平台 MCP 审批。

配置格式必须由调用方显式传入 `yaml`、`toml` 或 `json`。平台不再提供格式检测工具，也不会用 `unknown` 代替参数错误。

## 工具清单

| 工具名 | 参数 | 返回 | 默认策略 | 风险 | 用途 |
| --- | --- | --- | --- | --- | --- |
| `push_task_list` | `sourceMark?`、`nameContains?`、`source?`、`status?`、`offset=0`、`limit=20` | `PushTaskPageVo` | `ALLOW` | `LOW` | 按更新时间倒序分页查询摘要，不返回完整配置 |
| `push_task_get` | `taskId` | `PushTaskVo` | `ALLOW` | `LOW` | 按 ID 查询完整配置、格式和当前运行轮次 |
| `push_task_get_log` | `taskId`、`logType`、`tailLines=100` | `Map<String,Object>` | `ALLOW` | `LOW` | 返回脱敏日志、本轮运行信息和截断标记 |
| `push_task_diagnose` | `taskId` | `PushTaskDiagnosticResultVo` | `ALLOW` | `LOW` | 只分析当前 `runId` 的进程状态和本轮日志 |
| `push_task_validate_config` | `config`、`format`、`metaFileName?`、`metaContent?` | `PushTaskValidationVo` | `ALLOW` | `LOW` | 执行静态、Meta 和 Vector 原生 `validate/test` 校验 |
| `push_task_create_and_start` | `request: PushTaskDto` | `PushTaskOperationVo` | `ASK` | `HIGH` | 创建并启动任务；按 `SYSTEM + mark` 幂等复用 |
| `push_task_update_and_restart` | `taskId`、`request: PushTaskDto` | `PushTaskOperationVo` | `ASK` | `HIGH` | 更新完整配置并重启，保留原 `source/mark` |
| `push_task_start` | `taskId` | `PushTaskOperationVo` | `ASK` | `HIGH` | 启动停止或崩溃状态的任务；运行中不重复启动 |
| `push_task_stop` | `taskId` | `PushTaskOperationVo` | `ASK` | `HIGH` | 停止任务；已停止时幂等成功并保留最后一轮 `runId` |
| `push_task_restart` | `taskId` | `PushTaskOperationVo` | `ASK` | `HIGH` | 无论当前状态都重新启动并生成新 `runId` |
| `push_task_delete` | `taskId` | `PushTaskOperationVo` | `ASK` | `HIGH` | 只按唯一 ID 删除单个任务 |

已删除的旧工具：`push_task_detect_format`、`push_task_list_by_source_mark`、`push_task_delete_by_source_mark` 和 `push_task_repair_and_restart`。本次升级不保留别名，旧客户端必须同步修改。

## 查询与详情

```json
{
  "sourceMark": "data-push:chat-001:user-event",
  "nameContains": "用户事件",
  "source": "SYSTEM",
  "status": "running",
  "offset": 0,
  "limit": 20
}
```

- `limit` 最大为 100；结果按更新时间倒序。
- 列表仅返回 `PushTaskPageVo.items` 摘要，不包含配置正文；需要配置或格式时继续调用 `push_task_get`。
- `sourceMark` 对应 Vectum 的 `mark`，为精确匹配；`nameContains` 不区分大小写。
- `status=running` 同时匹配 `running` 和 `running[error]`，需要精确状态时可传完整状态文本。
- 查询和操作不限制任务来源；智能体新建任务仍固定为 `SYSTEM`。

`push_task_get` 返回完整 `PushTaskVo`，包括：

```text
id, name, description, source, mark, config, format, status, pid,
updateTime, currentRunId, runStartedAt, validationStatus
```

## 创建与更新参数

```json
{
  "request": {
    "name": "持续分析数据接入",
    "description": "将业务事件写入分析存储",
    "config": "sources: {}\nsinks: {}",
    "format": "yaml",
    "source": "SYSTEM",
    "mark": "data-push:chat-001:user-event",
    "candidateDigest": "<push_task_validate_config.candidateDigest>",
    "metaDigest": "<push_task_validate_config.metaDigest>",
    "validationDigest": "<push_task_validate_config.validationDigest>",
    "metaFileName": "user_event.json",
    "metaContent": "<config_read 返回的已发布 Meta 原文>",
    "repairRound": 0
  }
}
```

| 字段 | 说明 |
| --- | --- |
| `name` | 任务名，创建和更新必需 |
| `description` | 任务说明 |
| `config` | 完整 YAML/TOML/JSON 配置文本，必需 |
| `format` | `yaml`、`toml` 或 `json`，MCP 创建和更新必填；`yml` 会规范化为 `yaml` |
| `source` | 智能体创建时必须严格为 `SYSTEM` |
| `mark` | 稳定来源标识；`source + mark` 只用于创建幂等 |
| `candidateDigest` | 候选配置正文的 SHA-256，必需且必须与正文一致 |
| `metaDigest` | 已发布 Meta 原文的 SHA-256，必需 |
| `validationDigest` | 本次平台校验结论摘要，必需 |
| `metaFileName` / `metaContent` | 服务端执行前复验已发布 Meta；ClickHouse 目标必需 |
| `repairRound` | 当前修复轮次，新建为 `0`，最大 `5` |
| `update_time` | 服务端维护，调用方通常不提交 |

创建规则：

- 同一 `SYSTEM + mark` 已存在且配置正文和格式一致时复用任务；任务未运行时启动它。
- 同标识但配置正文或格式不同，创建工具拒绝继续，必须显式走 `push_task_update_and_restart`。
- 同一标识存在多个任务时 fail-closed，不自动选择或删除。

更新规则：

- 只覆盖名称、描述、配置和格式；请求中没有提供的 `source/mark` 保持原值。
- MCP 会丢弃调用方提交的 `source/mark` 并校验其不能改变任务归属。
- 更新后立即重启并返回新的 `runId`。

## 生命周期返回

所有写工具返回统一的 `PushTaskOperationVo`：

```json
{
  "action": "restart",
  "taskId": 12,
  "previousStatus": "running",
  "status": "running",
  "changed": true,
  "pid": 4321,
  "currentRunId": "4cbf9e1a-...",
  "runStartedAt": "2026-10-30T10:00:00Z"
}
```

- `push_task_start`：运行中返回 `changed=false`，不重复启动。
- `push_task_stop`：已停止返回 `changed=false`；保留最后 `currentRunId` 供查看最后一轮日志。
- `push_task_restart`：总是停止必要的旧进程并启动，产生新 `runId`。
- `push_task_delete`：仅接受唯一 `taskId`，返回 `action=delete`、`status=deleted`；不提供备注或通配批量删除。

## 配置校验

```json
{
  "config": "sources:\n  src:\n    type: demo_logs\nsinks:\n  out:\n    type: console\n    inputs: [src]",
  "format": "yaml",
  "metaFileName": "",
  "metaContent": ""
}
```

`push_task_validate_config` 依次执行：

1. 按显式格式解析 YAML/JSON/TOML，并确认 `sources`、`transforms`、`sinks` 是以组件 ID 为键的映射。
2. 检查 `inputs` 存在、无自引用、无循环；ClickHouse 目标必须来自已发布 Meta，数据库为 `zenvis`。
3. 检查业务字段与 Meta Attribute、保留字段、硬编码密钥和测试用例。
4. 在隔离临时目录使用生产同版本 Vector 执行 `validate --no-environment --disable-env-var-interpolation`，再执行 `vector test`。
5. 缺失环境变量仅向子进程注入非敏感占位值；占位值不落盘、不返回给模型。

返回结构：

| 字段 | 说明 |
| --- | --- |
| `passed` | 静态规则、原生校验、摘要匹配和测试是否全部通过 |
| `blocked` | 校验服务或 Vector 不可用；必须 fail-closed 停止创建和修复 |
| `format` | 规范化后的 `yaml`、`toml` 或 `json` |
| `candidateDigest` | 平台按提交配置计算的 SHA-256 |
| `metaDigest` | 平台按 Meta 原文计算的 SHA-256 |
| `validationDigest` | 锁定本次校验结论的摘要 |
| `vectorVersion` | 实际执行校验的 Vector 版本 |
| `diagnostics[]` | `code`、`severity`、`source`、`path`、`message`、`repairHint` |
| `tests` | `present`、`total`、`passed`、`failed`、`cases` |
| `normalizedConfig` | 可选规范化配置；创建仍使用完整候选正文 |

含 Transform 或 ClickHouse 写入时，必须至少包含一个合法样例测试和一个异常/死信测试。纯 `source → sink` 原始转发可豁免测试，但仍要执行拓扑、Meta 和原生校验。

## 日志与诊断

```json
{"taskId": 12, "logType": "system", "tailLines": 100}
```

- `logType` 仅支持 `console`（Vector stdout / `info.log`）或 `system`（Vector stderr / `error.log`）。
- 返回内容经过密码、Token、Bearer 和 URI 用户信息脱敏，并包含 `truncated`、`totalLines`、`returnedLines`。
- 同时返回 `currentRunId`、`runStartedAt` 和任务状态。

`push_task_diagnose` 区分配置错误、VRL/测试错误、进程崩溃、启动中，以及连接拒绝、认证、DNS、TLS、权限和目录缺失等外部阻塞。只分析当前 `runId` 启动标记之后的日志。

## 推荐调用流程

```text
config_tree(type="meta") + config_read
  → 生成完整候选和显式 format
  → push_task_validate_config
  → push_task_list(sourceMark, source=SYSTEM)
  → push_task_get（已有任务时）
  → push_task_create_and_start 或 push_task_update_and_restart（审批）
  → push_task_get
  → push_task_diagnose
  → 成功记录或 repairRound + 1
```

用户明确查看或操作任务时，按 ID 使用专用工具；不要用备注猜测目标任务。成功记录必须包含真实 `taskId`、`runId`、`validationDigest`、测试摘要和本轮日志摘要。

## Vectum REST 对应接口

| 能力 | 接口 |
| --- | --- |
| 分页筛选 | `GET /vectum/api/v1/task/query` |
| 完整详情 | `GET /vectum/api/v1/task/{id}/view` |
| 创建 | `POST /vectum/api/v1/task/add` |
| 更新 | `PUT /vectum/api/v1/task/{id}` |
| 启动 / 停止 / 重启 | `POST /vectum/api/v1/task/{id}/start|stop|restart` |
| 兼容旧页面切换 | `POST /vectum/api/v1/task/{id}/toggle` |
| 日志 | `GET /vectum/api/v1/task/{id}/log?log_type=console|system` |
| 诊断 | `GET /vectum/api/v1/task/{id}/diagnostics` |
| 隔离校验 | `POST /vectum/api/v1/task/validate` |

Vectum REST 对历史调用允许缺省 `format`，但仅在内容能被可靠识别时兼容；无法识别或格式非法时返回明确错误，不再产生 `unknown`。历史任务在读取时推导格式，在下一次更新时持久化。
