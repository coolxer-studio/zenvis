# 数据推送 MCP 工具

`PushTaskMcpTool` 注册 6 个面向受管数据推送任务的工具。它们通过 ZenVis 服务层访问 Vectum，并强制使用 `source=SYSTEM` 和稳定 `mark` 标识任务归属。

## 工具清单

| 工具名 | 参数 | 返回 | 默认策略 | 风险 | 用途 |
| --- | --- | --- | --- | --- | --- |
| `push_task_create_and_start` | `request: PushTaskDto` | Boolean | `ASK` | `HIGH` | 创建并立即启动受管任务 |
| `push_task_list_by_source_mark` | `sourceMark: String` | `List<PushTaskVo>` | `ALLOW` | `LOW` | 查询同一来源标识的系统任务 |
| `push_task_delete_by_source_mark` | `sourceMark: String` | Boolean | `ASK` | `HIGH` | 删除同一来源标识的系统任务 |
| `push_task_get_log` | `taskId: Integer`、`sourceMark: String`、`logType: String` | `Map<String,Object>` | `ALLOW` | `LOW` | 读取最新受控日志 |
| `push_task_repair_and_restart` | `taskId: Integer`、`sourceMark: String`、`request: PushTaskDto` | Boolean | `ASK` | `HIGH` | 更新完整配置并重新启动 |
| `push_task_detect_format` | `content: String` | String | `ALLOW` | `LOW` | 检测 `yaml`、`toml` 或 `json` |

旧的组件能力、配置生成、通用验证类推送工具已经下线，当前工具 Schema 不包含 `validationId`。配置内容的业务正确性应由对应 Skill、专项验证和真实运行日志共同确认。

## PushTaskDto

```json
{
  "request": {
    "name": "持续分析数据接入",
    "description": "将业务事件写入分析存储",
    "config": "sources: {}\nsinks: {}",
    "source": "SYSTEM",
    "mark": "data-access:chat-001:user-event"
  }
}
```

| 字段 | 说明 |
| --- | --- |
| `name` | 任务名，创建和修复必需 |
| `description` | 说明 |
| `config` | 完整 YAML/TOML/JSON 配置文本，必需 |
| `source` | 必须严格为 `SYSTEM` |
| `mark` | 稳定来源标识，必须与顶层 `sourceMark` 一致 |
| `update_time` | 服务端维护，调用方通常不提交 |

`PushTaskVo` 返回 `id`、名称、说明、来源、标识、配置、状态、进程 ID 和更新时间。

## 推荐工作流

创建前：

```text
push_task_list_by_source_mark
  → 确认不存在冲突任务
  → push_task_detect_format
  → 由专项流程验证完整配置
  → 展示配置与影响范围
  → push_task_create_and_start（审批）
  → 再次查询任务
  → push_task_get_log(logType=system)
```

失败修复：

```text
push_task_get_log
  → 向用户展示真实失败证据
  → 解释具体原因
  → 展示每一项配置旧值和新值
  → push_task_repair_and_restart（审批）
  → 查询状态和 system 日志复核
```

删除：

```text
push_task_list_by_source_mark
  → 展示将删除的任务
  → push_task_delete_by_source_mark（审批）
```

## 日志结果

`push_task_get_log` 只接受 `console` 或 `system`。工具先校验：

- `taskId` 存在。
- 任务 `source` 是 `SYSTEM`。
- 任务 `mark` 与 `sourceMark` 精确相等。

返回 Map 包含：

| 字段 | 说明 |
| --- | --- |
| `taskId` | 任务 ID |
| `sourceMark` | 来源标识 |
| `logType` | 日志类型 |
| `taskStatus` | 当前任务状态 |
| `content` | 清洗后的最新日志内容 |
| `truncated` | 是否截断 |

工具只保留日志尾部有限内容，并掩码密码、Authorization 和 Bearer Token。日志仍可能含业务敏感数据，Agent 只应摘录诊断所需部分。

## 调用示例

查询冲突：

```json
{
  "sourceMark": "data-access:chat-001:user-event"
}
```

读取系统日志：

```json
{
  "taskId": 12,
  "sourceMark": "data-access:chat-001:user-event",
  "logType": "system"
}
```

修复并重启：

```json
{
  "taskId": 12,
  "sourceMark": "data-access:chat-001:user-event",
  "request": {
    "name": "持续分析数据接入",
    "description": "修复字段映射",
    "config": "sources: {}\nsinks: {}",
    "source": "SYSTEM",
    "mark": "data-access:chat-001:user-event"
  }
}
```

## 安全约束

- `mark` 是受管任务所有权边界，不能用模糊或用户可随意覆盖的值。
- 创建后必须查询状态和 `system` 日志，Boolean 成功不代表任务已稳定运行。
- 没有真实日志证据时不能调用修复工具。
- 修复请求必须提交完整配置，不能只提交局部 Patch。
- 下游认证由服务端 `app.services.data.bearer-token` 处理，工具参数不携带 Token。
