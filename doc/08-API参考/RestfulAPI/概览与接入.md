# RESTful API 概览与接入

ZenVis RESTful API 面向 Web 前端、自动化程序和第三方业务系统。除明确标记为公开的接口外，`/api/v1/**` 使用 Session/Cookie 或 REST API Bearer Token 认证。

## 服务入口

| 项目 | 默认值 |
| --- | --- |
| 后端地址 | `http://localhost:11001` |
| API 前缀 | `/api/v1` |
| Swagger UI | `http://localhost:11001/swagger-ui/index.html` |
| OpenAPI JSON | `http://localhost:11001/v3/api-docs` |
| JSON 字段 | `snake_case` |
| 字符编码 | UTF-8 |

Swagger 反映当前运行实例生成的接口和 Schema；本目录补充业务边界、调用顺序、兼容约定以及跨 Controller 的关系。

## 认证方式

### Session/Cookie

浏览器先调用 `POST /api/v1/system/login/sign-in`，后续请求携带服务端返回的 `JSESSIONID`。这是 ZenVis 管理界面的默认方式。

### REST API Bearer Token

服务对服务调用可设置：

```bash
API_BEARER_TOKEN=<独立随机令牌>
API_BEARER_USER=admin@admin.com
```

调用时携带：

```http
Authorization: Bearer <API_BEARER_TOKEN>
```

`API_BEARER_USER` 必须对应现有系统用户，权限和审计身份按该用户执行。生产环境没有默认 Token；未配置、Token 错误或映射用户不存在时请求会被拒绝。

### 公开接口

以下两个接口不要求 Session 或 Bearer Token：

- `POST /api/v1/public/business-services/heartbeat`
- `POST /api/v1/public/business-services/events`

公开仅表示应用层不校验登录。生产部署仍应通过网关、网络策略、限流和来源控制保护接口，完整契约见[业务服务](/08-API参考/RestfulAPI/业务服务.md)。

### MCP Bearer Token 不是 REST Token

`MCP_BEARER_TOKEN` 只保护 `/sse` 和 `/mcp/message`，不能替代普通 REST API 的 `API_BEARER_TOKEN`。MCP 接入见 [MCP Tool 总览与接入](/08-API参考/MCPtool/总览与接入.md)。

## 请求约定

### Content-Type

- 普通 JSON：`application/json`
- 文件上传：`multipart/form-data`
- 下载、流式响应或图片：按具体接口返回的媒体类型处理
- DIH Chat：请求为 JSON，响应为 NDJSON 事件流

### 字段命名

JSON 和常规查询字段使用 `snake_case`，例如：

```json
{
  "per_page": 20,
  "service_code": "order-service",
  "base_revision": 3
}
```

部分历史 GET 查询同时兼容 Java 属性形式，例如分页的 `perPage`。新接入统一使用 `per_page`。

### 分页

标准分页请求：

| 字段 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `page` | integer | `1` | 从 1 开始 |
| `per_page` | integer | `10` | 每页条数 |

标准分页数据：

```json
{
  "rows": [],
  "total": 0
}
```

个别检索接口使用 `size` 控制返回数量，以对应接口说明为准。

## 统一响应

大部分业务接口返回：

```json
{
  "status": 0,
  "msg": "请求成功",
  "data": {}
}
```

| 字段 | 说明 |
| --- | --- |
| `status` | 业务状态码；`0` 表示成功，`101` 通常表示需要重新登录 |
| `msg` | 业务提示或错误信息 |
| `data` | 业务数据、列表或 `null` |

不能只根据 HTTP 200 判断业务成功，调用方还必须检查 `status`。以下接口不使用标准包装：

- 登录验证码直接输出图片。
- `GET /api/v1/config/{type}/get` 直接返回配置对象。
- 报表导出直接返回文件字节流。
- 插件日志和 DIH Chat 使用流式响应。
- 报表并发冲突使用 HTTP 409，并在响应数据中返回当前文档。

## 错误处理

建议调用方按以下顺序处理：

1. 网络异常或非 2xx HTTP 状态。
2. JSON 响应中的 `status != 0`。
3. HTTP 401/业务状态 101 时重新认证。
4. HTTP 409 时使用服务端返回的最新修订重新合并报表内容。
5. 流式接口逐行解析事件，收到 `error` 或连接中断时保留已接收内容并展示失败原因。

## 前端 API 模块

当前前端通过 `src/service/request-wrapper.ts` 统一封装 Axios，请求方法集中在以下模块：

| 模块 | 主要接口域 |
| --- | --- |
| `api-analysis-task.ts` | AI 分析任务、模型、Skill、任务审批和调用审计 |
| `api-dashboard.ts` | 首页概览和实体统计 |
| `api-dih.ts` | Chat、会话、报表、Skill 和 MCP 审批 |
| `api-entity-analytics.ts` | 实体分析十类查询 |
| `api-policy.ts` | 配置树、Schema、读取、修改、应用和文件操作 |
| `api-retrieval.ts` | 检索、规则、Meta、候选值和自动补全 |
| `api-system.ts` | 系统信息、品牌资源和看板 |
| `api-user.ts` | 登录、退出、公钥和密码修改 |

报表导出由报表页面直接请求 `/api/v1/dih/chat-session/{sessionId}/report/export/{format}`。新增前端调用时优先扩展对应领域模块，不在 Vue 组件中散落重复请求代码。

## 调用示例

### Bearer Token 查询首页概览

```bash
curl -H "Authorization: Bearer ${API_BEARER_TOKEN}" \
  http://localhost:11001/api/v1/dashboard/home/overview
```

### 分页查询动态实体

```bash
curl -H "Authorization: Bearer ${API_BEARER_TOKEN}" \
  "http://localhost:11001/api/v1/entity/device/list?page=1&per_page=20"
```

### TypeScript

完整可复用示例保存在 `doc/08-API参考/RestfulAPI/示例/skill-api.ts`。核心调用方式如下：

```ts
const response = await fetch("/api/v1/dih/skills/list?page=1&perPage=20", {
  credentials: "include",
  headers: {
    Authorization: `Bearer ${apiToken}`,
    "Content-Type": "application/json"
  }
});

const body = (await response.json()) as ResponseWrap<PageRowsVo<SkillVo>>;
if (!response.ok || body.status !== 0) {
  throw new Error(body.msg || `HTTP ${response.status}`);
}
return body.data;
```

## 接入排障

- 401 或 101：检查 Token、Session、`API_BEARER_USER` 和用户状态。
- 返回字段与文档不一致：先查看运行实例的 Swagger，再确认前后端是否来自同一版本。
- 分页为空：确认 `page` 从 1 开始，并检查 `per_page`、过滤条件和实体逻辑名称。
- 动态实体失败：实体和字段必须使用 Meta 中的逻辑名称，不能使用物理表字段。
- 上传失败：确认使用 `multipart/form-data` 且字段名为接口要求的 `file`。
- Chat 无增量：确认客户端按行解析 NDJSON，而不是等待完整 JSON。
