## 标识与时间

- `id`：来源系统的业务资产标识，可读、可复制，用于业务检索和关联。
- `zenvis_id`：平台自动生成的记录 UUID，用于详情、修改和删除 API。
- `update_time`：来源系统的资产更新时间，也是默认排序列。
- `insert_time`：业务上报声明的入库时间。
- `zenvis_insert_time`：Zenvis 实际接收时间，由平台维护，插件不写入。

## 数据接入边界

本版本按明确需求恢复了 `02_push-task/push_asset.yaml` 模拟任务。安装后平台会创建并
启动“资产模拟数据生成与入库”，默认每 5 秒从 21 条静态样例中随机选择一条，补充
业务标识和时间后直接写入对应 ClickHouse 表。该任务只用于开发、演示和页面验收，
会持续产生新记录；不需要时必须在“数据推送服务”页面停用。

模拟任务支持 `ASSET_DEMO_INTERVAL_SECONDS`、`CLICKHOUSE_ENDPOINT`、
`CLICKHOUSE_DATABASE`、`CLICKHOUSE_USER`、`CLICKHOUSE_PASSWORD` 环境变量。
解析异常会输出到任务日志。由于输入是插件内置静态样例，它不引入 Kafka 或 DLQ。

本版本仍没有可作为生产依据的来源协议、字段顺序、必填约束、鉴权方式、重试语义或
Kafka 主题约定。收到真实接入规范后，应新增两个独立 YAML 服务：

1. 来源到 Kafka：原样发送记录，不解析、重命名或丢弃业务字段。
2. Kafka 到 ClickHouse：按 Entity 校验、转换和写入；失败记录进入插件独立 DLQ。

建议默认 DLQ topic 为 `com-coolxer-plugin-asset-dead-letter`，并允许通过 `PLUGIN_ASSET_DLQ_TOPIC` 覆盖。DLQ 事件必须保留原始 `message`、失败组件、失败原因和可操作的校验信息。重放前修复数据或转换规则，再发送回正常来源 topic；DLQ 不得直接回流自身。

所有 ClickHouse sink 必须使用：

```yaml
auth:
  strategy: basic
  user: "${CLICKHOUSE_USER:-default}"
  password: "${CLICKHOUSE_PASSWORD:-SFGEfSVVMcUHCBCjKmzJ}"
```

## UI 与调查

- 低代码应用包含十个实体列表、规则配置和手动录入入口。
- 每个实体有独立详情配置，使用 `/api/v1/entity/{entity}/{record_id}/view`。
- `asset_host`、`asset_pc`、`asset_iot`、`asset_mobile` 的 `lan_ip` 与 `wan_ip` 链接到 IP 命中调查页。
- IP 调查在每个实体内对内外网字段使用 OR 语义，单条记录最多计数一次。

## 升级限制

平台增量升级禁止修改已安装 Entity 的表名、引擎、排序键、分区键以及已有字段的 ID、列名和类型。为保持从 `1.2.3` 可升级，当前物理表仍保留历史 `PARTITION BY id`。

若数据规模增长后需要按月分区，必须通过独立数据迁移实施：新建目标表、校验字段和数据量、回填、切换写入与查询、保留回滚窗口，最后再清理旧表。不要直接改 Meta 后上传升级包。

## 验证边界

静态验证包括 JSON/YAML 解析、模拟样例与 Meta 字段对齐、页面引用、详情/IP 链接、动态 API 测试、看板 JavaScript 编译和归档检查。模拟任务的实际启动、ClickHouse 写入以及页面实时展示必须在目标环境继续验证；真实来源、Kafka 和 DLQ 仍需等待生产接入规范。
