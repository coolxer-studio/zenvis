# HET-WAF-2516P Syslog 接入说明

## 1. 处理边界

本插件从 OneSOC 的 HET-WAF 接入内容中提取并独立建模，只处理惠尔特 HET-WAF-2516P 防火墙日志。默认接收地址为 `0.0.0.0:12516/UDP`，默认只接受来源 IP `192.168.42.234`，避免与 OneSOC 的公共 Syslog 端口和来源分流相互影响。

```text
HET-WAF-2516P Syslog
        │
        ├── source_ip 不匹配或 message 为空 ──▶ hetwaf2516p-dead-letter
        │
        └── 完整 JSON 外层事件 ──▶ hetwaf2516p-syslog-raw
                                      │
                                      ├── 公共规则结构 ──▶ het_waf_2516p_rule_event
                                      ├── DDoS / 未知格式 ─▶ het_waf_2516p_raw_event
                                      └── 解析失败 ────────▶ hetwaf2516p-dead-letter

演示任务（独立、可停止）
        │ 合成规则 / DDoS / 系统原文
        └── source_type=demo ──▶ hetwaf2516p-syslog-raw（复用同一转换入库链路）
```

规则事件采用“结构路由”而不是 `type` 白名单。只要消息符合已建模的公共字段结构，任意 `type` 都进入规则事件表；不匹配的消息不强行套用固定字段，完整进入原始事件表。

## 2. 契约矩阵

| 数据定义 | Entity | ClickHouse 表 | Kafka 主题 | UI 页面 | 结构化 |
| --- | --- | --- | --- | --- | --- |
| HET-WAF 公共规则事件 | `het_waf_2516p_rule_event` | `het_waf_2516p_rule_event` | `hetwaf2516p-syslog-raw` | 规则事件列表 / 规则事件详情 | 是 |
| HET-WAF 原始事件 | `het_waf_2516p_raw_event` | `het_waf_2516p_raw_event` | `hetwaf2516p-syslog-raw` | 原始事件列表 / 原始事件详情 | 是 |

两个实体均只使用一个 ClickHouse 表，平台自动补充 `zenvis_id` 和 `zenvis_insert_time`，Vector 不写入这两个保留字段。

## 3. 样例与字段映射

### 3.1 外层 Syslog

Vector Syslog source 将 UDP 报文解析为 JSON，再原样送入 `hetwaf2516p-syslog-raw`。关键外层字段如下：

```json
{
  "appname": "2026-07-21",
  "facility": "local7",
  "host": "HET-WAF",
  "hostname": "HET-WAF",
  "message": "08:57:45 WAF: 43.159.128.237:40284->www.xtszxyy.com dip=220.170.15.132 devicename=HET-WAF url=/ method=GET args= flag_field= block_time=0 http_type= attack_field=0 profile_id=4 rule_id=9 type=HTTP Conformity Rule severity=2 action=REJECT referer= useragent= post= equipment=1 os=1 browser=2 |",
  "severity": "warning",
  "source_ip": "192.168.42.234",
  "source_type": "syslog",
  "timestamp": "2026-07-21T00:57:45Z"
}
```

`timestamp` 必须是 RFC3339 时间，入库时统一转换为 UTC `DateTime64(3)`。`source_ip` 必须等于配置的 WAF 地址。

### 3.2 规则事件字段

消息前缀按以下顺序解析：

| 原始位置/键 | Meta 字段 | 类型 | 说明 |
| --- | --- | --- | --- |
| `HH:mm:ss` | `device_time` | `String` | 设备本地时分秒，保留原值 |
| 箭头左侧地址 | `client_ip` | `String` | 客户端 IPv4/IPv6 文本 |
| 箭头左侧端口 | `client_port` | `UInt16` | 0–65535，越界进死信 |
| 箭头右侧主机 | `request_host` | `String` | 可为空 |
| `dip` | `destination_ip` | `String` | WAF 保护目标地址 |
| `devicename` | `devicename` | `String` | 通常为 `HET-WAF` |
| `url` / `method` | `url` / `method` | `String` | 请求路径与 HTTP 方法 |
| `args` / `flag_field` | `args` / `flag_field` | `String` | 可为空，按原值保存 |
| `block_time` | `block_time` | `UInt32` | 厂商未说明单位，不换算 |
| `http_type` | `http_type` | `String` | 可为空 |
| `attack_field` | `attack_field` | `UInt16` | 0–65535 |
| `profile_id` | `profile_id` | `UInt64` | 防护配置编号 |
| `rule_id` | `rule_id` | `UInt64` | 规则编号，详情链接字段 |
| `type` | `type` | `String` | 不做枚举限制 |
| `severity` | `severity` | `UInt8` | 消息内级别代码，0–255 |
| `action` | `action` | `String` | 如 `REJECT`、`BLOCK` |
| `referer` / `useragent` / `post` | 同名字段 | `String` | 完整保留，可含空格 |
| `equipment` / `os` / `browser` | 同名字段 | `UInt16` | 厂商数字代码 |

外层 Syslog 字段映射为 `syslog_appname`、`syslog_facility`、`syslog_host`、`syslog_hostname`、`syslog_severity`、`syslog_source_ip`、`syslog_source_type`、`syslog_message`，完整接收时间映射为 `syslog_timestamp`。

规则事件表按 `(syslog_timestamp, rule_id, client_ip, client_port)` 排序。

### 3.3 原始事件字段

| Meta 字段 | 类型 | 说明 |
| --- | --- | --- |
| `syslog_timestamp` | `DateTime64(3)` | 外层 Syslog 接收时间，UTC 毫秒精度 |
| `event_type` | `String` | 从 `HH:mm:ss <type>:` 提取，无法识别为 `UNKNOWN` |
| `device_time` | `String` | 可识别的设备本地时分秒，否则空字符串 |
| `syslog_source_ip` | `String` | 发送端地址 |
| `syslog_host` | `String` | 外层 host |
| `syslog_severity` | `String` | 外层严重级别文本 |
| `syslog_appname` | `String` | 外层 appname |
| `syslog_facility` | `String` | 外层 facility |
| `syslog_hostname` | `String` | 外层 hostname |
| `syslog_source_type` | `String` | 外层 source_type |
| `syslog_message` | `String` | 完整原始消息，不做内部格式限制 |

原始事件表按 `(syslog_timestamp, event_type, syslog_source_ip)` 排序。DDoS 示例：

```text
07:03:24 DDoS:设备名称:HET-WAF 入侵ip:123.160.223.74 入侵端口:13623 被攻击ip:220.170.15.132 被攻击端口:443 协议类型:TCP 攻击类型:TCP Syn Flood 被攻击url: 被攻击域名: CDN ip:0.0.0.0 XFF ip:0.0.0.0 严重级别:高级 攻击次数:1
```

该消息保存 `event_type=DDoS`、`device_time=07:03:24`，其余内容完整留在 `syslog_message`。

## 4. Kafka 与死信

| 主题 | 用途 |
| --- | --- |
| `hetwaf2516p-syslog-raw` | 校验通过后的完整外层 Syslog JSON |
| `hetwaf2516p-dead-letter` | 来源、报文、JSON、时间、数值或结构转换失败的事件 |

死信主题使用独立默认名并可通过 `HET_WAF_2516P_DLQ_TOPIC` 覆盖，不能与 `hetwaf2516p-syslog-raw` 相同。Kafka sink 使用 `acks=-1`、重试和磁盘缓冲，避免短暂故障造成静默丢失。

Vector 写入死信时保留原始事件，并附带：

- `metadata.dropped.component_id`：失败转换组件；
- `metadata.dropped.message`：可操作的失败原因；
- `metadata.dropped.reason`：Vector 丢弃原因。

重放步骤：

1. 从死信记录的 `message` / 原始外层字段中取出原始 Syslog 事件；
2. 修复字段、时间或插件转换规则；
3. 将原始事件写回 `hetwaf2516p-syslog-raw`；
4. 按目标 offset 或时间窗口观察 `het_waf_2516p_rule_event` / `het_waf_2516p_raw_event` 是否入库。

不要将整个死信信封写回原始主题，否则会被视为非法外层 JSON 再次进入死信。历史补录建议使用独立消费组或定向 offset，避免从 `earliest` 重放已入库事件造成重复。

## 5. 演示数据推送

插件新增独立任务 `demo-data-to-kafka.yaml`，任务名为“惠尔特 HET-WAF 演示数据推送（正式上线后停止）”。该任务与正式 Syslog 接入任务、Kafka 转换入库任务互相独立，安装插件时会随插件自动启动。

处理方式：

1. `demo_logs` 每 `HET_WAF_2516P_DEMO_INTERVAL_SECONDS` 秒（默认 `2`）从内置样例中随机选择一条；
2. 合成事件覆盖 HTTP Conformity Rule、Signature Rule、ASCN Rule、Upload Rule、Sensitive Data Rule、Crawler Rule、DDoS 和系统原文；
3. 刷新外层 `timestamp`、消息内 `HH:mm:ss`、`source_ip`、`source_type` 和演示设备标识；
4. 写入正式原始主题 `hetwaf2516p-syslog-raw`，由现有 `waf-kafka-to-clickhouse.yaml` 完成校验、规则/原始事件分流和 ClickHouse 入库。

演示数据标识：

| 位置 | 标识 |
| --- | --- |
| 外层 `source_type` | `demo` |
| 外层 `host` / `hostname` | `HET-WAF-DEMO` |
| 规则事件 `devicename` | `HET-WAF-DEMO` |
| DDoS / 系统原文 | `syslog_message` 中以 `设备名称:HET-WAF-DEMO` 标识 |

演示任务不会改变 Meta、表结构、正式主题名或转换规则。停止该任务只会停止后续合成数据，不会停止 UDP Syslog 接入，也不会删除已经入库的历史演示记录。正式上线时在“数据推送服务”中停止该任务即可；如需清理既有演示数据，可按 `syslog_source_type='demo'` 或 `syslog_host='HET-WAF-DEMO'` 识别。

## 7. 部署与验证

部署前提：

- Kafka、ClickHouse 与 Vectum 正常；
- HET-WAF-2516P 的 Syslog 目标指向 Vectum 所在主机的 `12516/UDP`，或同步修改 `HET_WAF_2516P_SYSLOG_ADDRESS`；
- 防火墙发送端地址与 `HET_WAF_2516P_SOURCE_IP` 一致；
- Vectum 进程可访问 Kafka 与 ClickHouse，且 ClickHouse 凭据通过环境变量注入。
- 未接入真实设备时，保持演示任务运行即可预览数据效果；正式上线后手动停止该任务。

默认 `deploy/docker-compose.yml` 的 `zenvis-service-vectum` 只发布了 `11002/TCP`。部署本插件时需补充 UDP 映射，例如：

```yaml
ports:
  - "${ZENVIS_INFRA_BIND_ADDRESS}:${VECTUM_PORT}:11002"
  - "${ZENVIS_INFRA_BIND_ADDRESS}:12516:12516/udp"
```

Kubernetes 部署需在 Vectum Service 中增加 `12516/UDP`，并按集群入口方式配置 LoadBalancer 或 NodePort。若修改监听地址、主题或来源 IP，还需将 `HET_WAF_2516P_*` 变量注入 Vectum 容器；这些变量有安全默认值，但不会自动写入平台部署配置。

建议部署后验证：

```bash
# 查看规则事件和原始事件是否入库
docker exec clickhouse-service clickhouse-client --query \
  "SELECT 'rule' AS kind, count() FROM zenvis.het_waf_2516p_rule_event UNION ALL SELECT 'raw', count() FROM zenvis.het_waf_2516p_raw_event"

# 检查最新规则事件
docker exec clickhouse-service clickhouse-client --query \
  "SELECT syslog_timestamp, rule_id, client_ip, type, action FROM zenvis.het_waf_2516p_rule_event ORDER BY syslog_timestamp DESC LIMIT 5"
```

本插件已完成静态契约校验和 Vector 测试，但未连接真实设备、Kafka 或 ClickHouse 执行端到端联调。
