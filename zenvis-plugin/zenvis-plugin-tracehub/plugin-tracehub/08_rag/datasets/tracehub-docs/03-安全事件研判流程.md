# 安全事件研判流程

## 目标

对用户提供的安全事件文本、JSON 或日志做只读、证据化的指标核验，回答四个问题：

1. 事件中真实存在哪些可查询指标？
2. TraceHub 当前快照是否命中这些指标？
3. 命中情报与事件时间、行为描述和关联关系是否一致？
4. 还存在哪些证据缺口和限制，下一步应做哪些只读调查？

不得把“未命中”直接写成“安全”，也不得虚构工具未返回的记录、时间或情报来源。

## 第一步：提取指标

只提取原文中明确出现的值，保留原值、上下文和出现位置。支持提取：

- IPv4 / IPv6；
- 域名（完整域名，不自动扩展到父域）；
- URL（保留路径、查询串和片段）；
- MD5、SHA-1、SHA-256、SM3、imphash、TLSH；
- 电子邮件地址。

提取原则：

- 不补全、不猜测、不生成用户未提供的指标。
- 对脱敏写法先标注原始形式，确认转换为标准形式后再查询；不要静默改写。
- 去重时保留原始大小写和表示形式，同时记录规范化后的查询值。
- 区分“事件主体”“受害者地址”“攻击者地址”“回连地址”“文件哈希”等语义。IP 角色不能由地址本身推断，必须来自事件上下文。
- 如果事件只给出时间、用户名、主机名或一段叙述，没有可查询指标，明确说明“没有可核验指标”，不要为凑结果制造 IOC。

## 第二步：选择工具与批量策略

| 指标 | 查询 |
| --- | --- |
| IP | `ioc_lookups` 查威胁情报；`ip_location_lookups` 查地理位置 |
| 域名、URL、哈希、邮箱 | `ioc_lookups` |
| 单个关键指标且需要更多明细 | `ioc_lookup` |

建议：

- 优先使用批量工具，减少工具调用次数。
- 将非 IP 指标放入同一批 `ioc_lookups`；将 IP 单独放入另一批，并按 IP 版本选择查询。
- `max_matches` 建议 5–10，避免明细过长；若 `truncated=true`，说明仍有未展示命中。
- 每次批量不超过 200 条；超出时按优先级分批。不要为了覆盖全部低价值指标耗尽工具预算。
- IP 同时查询 IOC 与地理位置，但两者结论分开陈述。

## 第三步：逐项解释状态

对每个指标记录：

| 状态 | 研判表达 |
| --- | --- |
| `matched` | “命中 N 条情报记录”，并列出证据 |
| `not_found` | “当前快照未命中”，不得写“安全”或“无威胁” |
| `not_covered` | “当前快照未覆盖该类型”，不得写“未命中” |
| `invalid` | “输入或类型无效”，不得作为威胁证据 |
| `library_unavailable` | “资源不可用，无法判断”，不得作为未命中 |

批量查询还要报告 `requested_count`、`valid_count`、`matched_count`；若存在无效项，要说明无效数量，而不是只报告命中数。

## 第四步：整理命中证据

每条命中至少整理：

- `matched_field`：命中的指标字段；
- `record_id`、`source`：记录身份与来源；
- `title`、`description`：情报摘要；
- `threat_types`：威胁类型；
- `severity`、`confidence`：来源给出的严重度和置信度，说明未知时写“未知”；
- `first_seen`、`last_seen`：情报时间范围；
- `attributes`：与事件相关的扩展字段，只在有值时引用；
- `match_count` 与 `truncated`：命中总量和截断情况。

不要只取第一条记录就代表全部命中。多条记录可能来自不同来源，结论可能冲突。

## 第五步：判断情报新鲜度

把 `last_seen` 与事件发生时间比较：

- 接近事件时间：可作为当时仍活跃或仍被收录的上下文。
- 明显早于事件时间：属于历史情报，不能直接说明事件发生时仍有效。
- `last_seen` 缺失：标为未知，不做新鲜度推断。
- `first_seen` 晚于事件时间：提示时间关系异常或数据覆盖问题，避免强行关联。

同时考虑 TraceHub 快照本身的生成时间。快照加载时间和记录时间不是同一概念。

## 第六步：关联分析

从证据中寻找可验证的关联：

- 多个指标是否出现在同一 `record_id` 或同一 `source`；
- 多个 IP 是否属于同一 ISP、地区或网段（仅作线索）；
- 域名、URL 与 IP 是否在同一情报记录中共同出现；
- 事件中的多个阶段是否重复使用同一基础设施；
- 命中类型是否与事件行为一致，例如下载哈希、回连域名、钓鱼 URL。

关联必须由工具返回字段或用户事件原文支撑。不要把地理位置当作归因，不要把同一 ISP 当作同一攻击者。

## 第七步：形成结论

选择且只选择以下结论之一作为主结论，可附加说明：

1. **情报命中**：至少一个事件指标有明确命中，且证据与事件上下文相符。
2. **情报未命中但证据不足**：查询成功但未命中，仍不能排除威胁；应说明快照覆盖和事件其他证据。
3. **输入或覆盖不足**：存在无效输入、类型未覆盖或批量不完整，当前无法完成核验。
4. **资源不可用**：TraceHub 或对应资源不可用，无法判断。
5. **无指标可查**：事件没有可核验指标，不能使用 TraceHub 给出指标级结论。

推荐输出：

```text
结论：<一句话定性，注明置信边界>

一、指标与查询结果
| 指标 | 类型 | IOC 状态 | 命中数 | IP 地理状态 | 说明 |
| --- | --- | --- | --- | --- | --- |

二、命中证据
| record_id | source | matched_field | title | threat_types | severity | confidence | last_seen |
| --- | --- | --- | --- | --- | --- | --- | --- |

三、关联分析
- <仅列出有证据支撑的关联>

四、证据缺口与限制
- <not_found / not_covered / invalid / unavailable / truncated / 快照时间等>

五、只读调查建议
- <例如扩大时间窗、核对日志原文、补充文件样本、查询其他情报源>
```

## 输出纪律

- 每个事实必须能对应到用户原文或工具返回。
- 明确区分“情报源严重度”与“本次事件风险”。
- 明确说明工具的查询条件、批量和截断。
- 不声称已阻断、隔离、封禁、删除文件或提交工单。
- 用户要求处置动作时，说明本 Skill 仅做只读研判，并给出平台内走审批或响应流程的建议。
